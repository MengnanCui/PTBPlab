关键信息

在电光云 dg50 分区的 RTX 5090 上把 GPU 自检完整跑了一遍（P137–P140）。GPU 上的正确性成立：269 项检查只有 1 项超出阈值，原因不是 GPU（见第二节）。但按 M7e 设计文档第五节的判据，同步 SCC 的跨结构批量不做：PTBP 的 Cu 阶段在 GPU 上串行比 32 个 CPU 进程慢 8.6 倍，GPU 运行里 93% 的时间留在 CPU；带 k 点的分组堆叠只有 0.96–1.07 倍，远低于 3 倍的门槛。

  • 正确性：65 个 DFTB+ 参考算例在 GPU 上 float64 全部通过；GPU 对 CPU（torch，float64）能量 ≤ 1.4e-14 Ha、力 ≤ 1.6e-14 Ha/Bohr、本征值 ≤ 1.0e-14 Ha；两次计算逐位相同；自动求导 GPU 对 CPU ≤ 2.9e-11；CUDA 之后 fork 的子进程正常结束。
  • 没过的一项：cpu li2_sk_tail [float64] 的电荷差 1.02e-10，阈值 1e-10，同一算例的能量差 5.6e-17、本征值差 1.4e-17。这个算例的电荷本来只准到 SCC 容差（M4a 报告：容差 1e-12 时 500 轮不收敛）。阈值不改，照实记下。
  • PTBP 的 Cu 阶段（66 个结构）：NumPy 单线程 22.0 s，32 个进程 1.56 s（由最大的结构 1.55 s 决定，16 个进程已经到 1.62 s）；GPU 串行 float64 13.4 s，其中 CPU 上的工作 12.4 s，GPU 的求解只有 0.94 s。
  • 求解本身在 GPU 上确实快：Σ(diag − fill) 从 NumPy 单线程的 8.65 s 降到 0.94 s（9.2 倍）；单个 Cu32 晶胞（288 个轨道、14 个 k 点）每轮 SCC 0.068 s，NumPy 单线程 0.50 s、k 点线程 0.12 s；批量 ≥ 128 的 eigh 在 float64、complex128 下快 3.6–24 倍。但 PTBP 的结构太小，求解只占阶段的一小部分。
  • 堆叠：只有 Γ 点的实矩阵组（33 个结构、N = 18）快 11.7 倍，可这一组在单线程下一共才 2.5 s；带 k 点的复数组 0.96–1.07 倍，因为每轮的时间有 53–84%（complex128）花在 CPU 上的费米能级。Cu32（N = 288）1.56 倍。
  • float32 不用于 PTBP：PTBP 阶段 |dE| 1.3e-4 Ha，4 个结构的 SCC 轮数不同（fcc 00 从 7 轮变成 45 轮）；Cu4 k8 100 轮不收敛；Cu32 的 complex64 堆叠对逐个的布居差 9.8e-3 e。
  • 268 / 269GPU 上通过的检查（1 项是阈值，不是 GPU）
  • 8.6 倍GPU 串行比 32 个 CPU 进程慢（PTBP 的 Cu 阶段）
  • 93%GPU 运行里留在 CPU 的工作
  • 1.26 元全部实测的费用（16.8 分钟卡时，实收 4.5 元/卡时）

一、怎么跑的

机器：电光云 dg50 分区的节点 c7g001、c7g002，每个作业 1 张 NVIDIA GeForce RTX 5090（32 GB，计算能力 12.0，170 个 SM，驱动 595.71.05），CPU 是 AMD EPYC 9J14。环境：Python 3.12.16，torch 2.14.1+cu130，NumPy 2.5.4（OpenBLAS 0.3.34），SciPy 1.18.1，ASE 3.29.0；pydftb 是分支 claude/inspiring-ride-zax2o7 的 c1a11bd，可编辑安装（所以 JSON 里 pydftb_commit 为空：同步时没有带 .git）。TF32 关闭，float32_matmul_precision = "highest"。

完整的自检拆成三个作业，各占一张卡同时运行；检查每次都会跑，所以计时作业用 --cases h2o 把参考算例压到一个：

li2_sk_tail：两个 Li 原子相距 14.8 Bohr，落在 SK 表之后的五次衰减尾巴里。GPU 对 DFTB+ 的参考是通过的（电荷差 6.9e-11，容差 1e-9）。GPU 对 CPU 的能量差 5.6e-17 Ha、力 2.1e-22 Ha/Bohr、本征值 1.4e-17 Ha，只有电荷差 1.02e-10 e。这个算例在默认 SCC 容差（1e-10）下 1 轮就停，容差 1e-12 时 500 轮不收敛（M4a 报告，两个后端相同），所以电荷只准到 SCC 容差的量级，两边舍入的不同就够越过固定的 1e-10。这不是 GPU 的错误；CPU_TOL 不改，照实记为一项未通过。

五、eigh 与 Cu 晶胞（P140）

  • eigh（GPU 对 NumPy，NumPy 用 16 个 BLAS 线程）：单个矩阵时 float64 与 complex128 在 N ≤ 144 慢（0.05–0.98 倍），N = 288 时 0.99 与 1.74 倍；批量 ≥ 128 时 float64 4.2–18 倍、complex128 3.6–24 倍、float32 14–147 倍、complex64 16–184 倍（最低的都是 N = 9）。float64 N = 72 的批量 1 与 16 两行是 46.6 与 739 倍，是 NumPy 那一次的计时异常（同一节点有别人的作业），不采用。
  • Cu 晶胞（每轮 SCC：NumPy 单线程 / k 点线程 / GPU float64）：Cu1 k14 0.075 / 0.091 / 0.050 s；Cu2 0.069 / 0.076 / 0.060 s；Cu4 k8 0.073 / 0.051 / 0.024 s；Cu8 k6 0.24 / 0.17 / 0.15 s；Cu32 k3 0.50 / 0.12 / 0.068 s。Cu32 在 100 轮内哪种方式都不收敛（计时上限 TIMING_MAX_SCC，与 M7e 在 CPU 上相同）。
  • Cu4 k8（T = 0）的 SCC 轮数：NumPy 28 轮，GPU float64 57 轮，float32 100 轮不收敛（M4d 在 CPU 上的 torch 是 37 轮）。能量差 7.2e-11 Ha。T = 0 的金属对舍入敏感，已在 M4a、M4d 记录，不是新问题。

六、按判据的决定

M7e 设计文档第五节的三条判据：

  1. 留在 CPU 的工作：GPU 运行里留在 CPU 的工作 12.4 s ≥ 进程池的 1.56 s，所以单把求解（包括堆叠）放到 GPU 上不会比现在快。要快只能做流水线，上限 0.94 s，即对进程池 1.66 倍。
  2. 堆叠的收益：要“明显大于 1（例如 ≥ 3 倍）”。带 k 点的组只有 0.96–1.07 倍，只有 Γ 点的小组达到（11.7 倍），而这一组在阶段里不到 12%，在进程池里本来就不是瓶颈。不满足。
  3. float32：T ≈ 0 的金属上轮数变化大、个别不收敛、堆叠的布居差到 1e-2。PTBP 不用 float32。

决定：不做同步 SCC 的跨结构批量与相应的 API。PTBP 的默认（CPU 进程池）不变。CPU 进程加 GPU 的流水线最多快 1.66 倍，代价是多进程共用一张卡、来回搬数据，还要另付 GPU 的费用；现在不做，等 PTBP 的结构明显变大时再评估。GPU 后端仍适合较大的单个体系（几百个轨道以上、k 点不多）和自动求导。
