关键信息

GPU 自检（pydftb gpu-check）修好并扩充了，在 NVIDIA GPU 上跑一次就能回答跨结构批量（M7e-2）值不值得做。JSON 每节之后原子地重写，任何一节出错都记下错误接着做，Ctrl-C 也留下已有的结果；计时照 --dtype；多了两项计时：PTBP 的 Cu DFTB 阶段逐个结构在 CPU 与设备上的时间，以及完整一轮求解在堆叠与逐个时的时间。PTBP 的阶段由新模块 validation/ptbp_workload.py 造出，不用数据文件。只用 NumPy 的计算路径不变（k 点约化的向量化逐位相同）。

  • 自检总能留下结果：JSON 每节之后原子地重写；一项计时出错、一组检查抛出异常或 Ctrl-C 时，JSON 都照样写出，其余各节照常运行（测试用伪造的错误逐一核对）。退出码 0 全部通过，1 有检查失败或某一节没能运行，2 中断。CUBLAS_WORKSPACE_CONFIG 在 CUDA 启动前设好；计时照 --dtype，没有 float64 的设备（MPS）只建 float32 与 complex64 的张量。
  • 在 CPU 上全部跑通（P131）：pydftb gpu-check --device cpu --dtype both 完整一次 320 项检查全部通过，约 15 分钟；--quick 35 项，约 3 分钟；从 wheel 装进仓库外的干净 venv 再跑 --quick，同样通过，不再取外层仓库的提交号。
  • 留在 CPU 的工作是决定性的数：PTBP 的 Cu 阶段（66 个结构）NumPy 单线程 27.1 s，4 个进程 7.49 s。torch 后端（这里在 CPU 上，一线程）25.3 s，其中只有求解（9.5 s）会搬到 GPU，其余 15.8 s（63%）留在 CPU：γ、原子对、费米能级、力与 ASE。所以设备串行的阶段至少 15.8 s，是进程池的 2.1 倍；CPU 进程与设备流水线的上限是 max(15.8 / 4, GPU 求解)。
  • 堆叠在 CPU 上没有收益：完整一轮求解在复数的分组上堆叠是逐个的 0.60–1.09 倍，只算 eigh 0.80–1.11 倍（M4d 量到 0.90–1.02），Γ 点的小矩阵组 2.9 倍（每个结构的 Python 开销）。GPU 上的数要看用户的 JSON。堆叠对逐个的布居差 ≤ 8.0e-15 e，本征值逐位相同。
  • 精度：torch 的 float64 对 NumPy |dE| ≤ 2.5e-11 Ha、|dF| ≤ 1.0e-11 Ha/Bohr、|dS| ≤ 5.2e-12，66 个结构的 SCC 轮数相同；float32 |dE| ≤ 1.1e-5 Ha、|dF| ≤ 6.1e-5 Ha/Bohr，6 个结构多一轮。
  • 没有做的：共用 SK 集合与后端只省 0.06%（P129），按计划的规则不做；同步 SCC 的跨结构批量（M7e-2）等你在 CUDA 上运行自检的 JSON。

开发细节一、做了什么
位置内容
validation/gpu_check.py
  • JSON 总能写出：run(json_path=…) 在每节之后调 write_report（同一目录里的临时文件，再 os.replace，权限与新建的文件相同）。_guard 包住每组检查与每项计时，记下耗时、max_rss_gb（CUDA 上还有 max_memory_allocated_gb），出错时记下错误与 traceback，显存不够时清缓存，接着做下一节；一组检查本身抛出异常时记为一个失败的检查。计时的每一行、每个结构也各自 try。结果的打印出错不会丢掉报告。
  • 退出码：0 全部通过，1 有检查失败或某一节没能运行（report["errors"]），2 中断：KeyboardInterrupt 时写出 "complete": false、"interrupted_in"，再交给 main 返回 2。
  • 次序：devices.resolve 之后先 devices.prepare（设好 CUBLAS_WORKSPACE_CONFIG），再查 capabilities。
  • 精度：timing_kinds 把 --dtype 变成矩阵类型（float64 → float64、complex128；float32 → float32、complex64），设备没有的记进 dtypes_skipped；time_cu、time_ptbp_stage、time_stacked_solve 对每种精度各算一遍（标签 device_float64 等）。
  • 环境（JSON 第 2 版）：pydftb 的版本与路径、命令行、scipy/ase/threadpoolctl 的版本、threadpool_info()、可用与物理核数、torch 的线程数、float32 矩阵乘法的精度、确定性开关；CUDA 上还有空闲显存、preferred_linalg_library、TF32 开关、驱动版本（nvidia-smi）。提交号只在 git 跟踪这个文件时记（git ls-files --error-unmatch），另记有无未提交的改动。
  • time_ptbp_stage：PTBP 的 Cu 阶段逐个结构，每个结构照 PTBP 的做法新建计算器再 get_forces()（能量、力、应力）。方式 numpy_1、numpy_kthreads（--workers 个 k 点线程）、numpy_procs（spawn 的进程池，每个一线程，先大后小，所有工作进程预热完、在屏障处会合之后才开始计时）、device_<dtype>（先算一个结构不计时，记为 cold_start_s）。每个结构记耗时、引擎的分项、SCC 轮数、是否收敛、fill 的时间（计时期间临时包住 pydftb.solvers.fill）、对 numpy_1 的 |dE|、|dF|、|dS|。汇总：和、平均、进程池的实测与模拟（LPT）完成时间、设备运行里留在 CPU 的工作 Σ(wall − diag + fill)、设备的求解 Σ(diag − fill)、流水线的上限 max(CPU 工作 / P, 设备求解)，以及对进程池、对 numpy_1 / P 的比。
  • time_stacked_solve 取代 time_stacked：输入是工作负载里真实的 H0、S（引擎的 _setup，torch 后端，放在设备上）。分组：Γ 点 N = 18（实数）、beta-Sn N = 18（复数）、bcc 与 fcc N = 9（复数），另有 CU_CELLS 的 5 个晶胞各 8 个 EOS 副本（N = 9–288）。逐个：每个结构 TorchSolver 的 prepare、solve、_populations；堆叠：一次 prepare、一次 eig、一次拷回主机、每个结构各自 fill、一次密度，布居用块权重矩阵乘一次。计 prepare、一轮、带 W 的最后一次、单独的 eigh（M4d 的那一列）与 fill，给出收益与最大 |Δε|、|Δμ|、|Δq|。显存守卫：CUDA 上空闲显存的一半，CPU 上 4 GiB；在 deterministic 下运行，CPU 上 torch 一线程。
  • 结论：verdicts 给出设备每个结构对 CPU 进程池的比、留在 CPU 的份额与流水线的上限、每组堆叠的收益，写进 JSON 并打印在最后。命令行多了 --timings（默认 eigh,cu,ptbp,stacked）与 --workers。
validation/ptbp_workload.py（新）PTBP 的 Cu 阶段：6 个相（dimer、AA-graphite、diamond、beta-Sn、bcc、fcc）的中心晶胞与分数坐标取自 dft/dft.xyz，11 个 EOS 体积 V/V0 = 0.80 + 0.04 i，晶胞按体积比的立方根缩放；k 网格是 PTBP 的规则（3000 K 的 Boltzmann 权重 < 0.1 的三个相只用 Γ 点，其余 int(5·2π|bi|)）；PTBP_OPTIONS 与 calculator(structure, **overrides) 是 PTBP 的 _pydftb_calculator 的参数，SK 集合用包里的 ptbp_hcocu（Cu-Cu 已在 package-data 里）。structures(quick=True) 取第 0、5、10 个 EOS 点。
kpoints.pyreduce_time_reversal 向量化：每对 {k, −k} 在 [0, 1) 里的代表取字典序较小的一个，np.unique(axis=0) 分组，按第一次出现的次序排列；每对的权重从它第一个点的权重起，按输入次序用 np.add.at 加上其余的点，与原来的循环是同一串浮点运算（带符号的零也一样）。163 的网格从 6.2 ms 降到 2.3 ms（本机，20 次中最短的一次）。
测试tests/test_gpu_check.py（重写，15 项）、tests/test_kpoints.py（新，20 项）、tests/test_ptbp_workload.py（新，4 项），PTBP 的 tests/test_ptbp_workload.py（新，3 项）；见第四节。

二、怎么用与 JSON 的读法

pip install ./pydftb torch            # 这个分支的 pydftb，加上 CUDA 版的 torch
pydftb gpu-check --dtype both --json gpu_check.json
pydftb gpu-check --quick --json quick.json          # 先试一遍，几分钟
pydftb gpu-check --timings ptbp,stacked --workers 8 # 只做这两项计时，进程池 8 个进程
  • JSON 的结构：environment；sections（每节的耗时、内存峰值、错误）；checks；timings 里的 eigh、cu、ptbp（structures 是每个结构每种方式的一行，summary 是汇总）与 stacked；verdicts；complete、ok、errors。
  • 先看留在 CPU 的工作：timings.ptbp.summary.device_float64 的 cpu_work_s 与 numpy_procs.makespan_s。若前者除以进程数 P 仍不小于后者，单把求解放到 GPU 上（包括堆叠）不会比现在的进程池快，M7e-2 要把这部分分给 CPU 进程、与 GPU 的求解流水线化，上限是 pipeline_bound_s。
  • 再看堆叠的收益：timings.stacked 每组的 iteration.gain（一轮完整求解）与 eigh.gain（只算 eigh，对照 M4d）。明显大于 1（例如 ≥ 3）而且 pipeline_bound_s 小于进程池的时间，才值得做同步 SCC。
  • float32：device_float32 的 max_dE、max_dF 与 unconverged 决定 GPU 上能不能用 float32。
  • 中断与出错：Ctrl-C 之后的 JSON 是可用的（"complete": false，interrupted_in 指出停在哪一节）；某一节出错时它的 error 与 traceback 在 sections 里，其余各节照常。
  • 自己的脚本：time_ptbp_stage 的进程池用 spawn，调用它的脚本要有 if __name__ == "__main__":（坑 202）。

  • 4 个进程同时运行时每个结构慢约 10%（29.85 对 27.08 s），完成时间 7.49 s 与先大后小的排程模拟（7.47 s）一致。k 点线程只快 10%：γ、力与 N = 9–18 的小矩阵运算都是串行的。

各节的耗时（完整，CPU）：参考与对照 float64 15 s、float32 13 s，eigh 219 s，cu 163 s，ptbp 108 s，stacked 346 s，合计约 15 分钟；--quick 约 3 分钟。wheel 装进干净 venv 的 --quick：35 项检查全部通过，pydftb_commit 为 null，pydftb_path 指向 venv，JSON 的权限 0644。

四、测试与门槛

tests/test_gpu_check.py（重写，15 项，没有 torch 时跳过）：

  • 检查在 CPU 上全部通过，人为的偏差让它以 1 退出（M4d 的两项，改查 JSON 第 2 版与 complete）。
  • JSON 照样写出：一项计时出错（错误与 traceback 在 sections 里，下一节照常，退出码 1）；一组检查抛出异常（记为一个失败的检查，其余检查照常）；Ctrl-C（退出码 2，"complete": false，interrupted_in，没有留下临时文件，权限与新建的文件相同）。
  • --dtype both 时四项计时都收到两种精度；仿 MPS 的能力（没有 float64）时只计 float32 与 complex64，也不做 float64 的检查；没有复数时 complex64 也跳过。未知的 --timings 与 --workers 0 被拒绝。
  • 没有 git 时照常；装在另一个仓库里的副本不取那个仓库的提交号。
  • 小的 PTBP 阶段（Γ 点的 dimer 与 4×4×4 网格的 bcc，1 个进程，两种精度）：k 点线程与进程池对 NumPy 逐位相同，torch 的 float64 ≤ 1e-8，汇总、先大后小的次序与结论的各项；LPT 排程。
  • 堆叠对逐个（实数与复数的分组，两种精度）：float64 ≤ 1e-12，显存守卫；Cu 晶胞与 eigh 的计时（M4d 的两项，改为两种精度）。

tests/test_kpoints.py（新，20 项，三个环境都跑）：新旧约化逐位相同，18 种网格（含 Γ 居中），打乱、平移、重复与带权重的输入，带符号的零、接近 1 的分量、−0.0 的权重与空输入。tests/test_ptbp_workload.py（新，4 项）：66 个结构、冻结的 k 网格、N、体积比与分数坐标、计算器的参数。PTBP 的 tests/test_ptbp_workload.py（新，3 项）：与 dft/dft.xyz 的晶胞和坐标差 ≤ 1e-8 Å，k 网格与 make_tasks 的相同，计算器的参数与 utils.engines._pydftb_calculator 的相同（NumPy 与 torch 的设置）。

五、与设计的偏差

  • 退出码：设计写 “1 有检查失败”。某一节没能运行（例如一项计时出错）也返回 1，因为那样的 JSON 缺了要回答的数；节的名字在 report["errors"] 里。
  • JSON 的权限：原子写起初用 tempfile.mkstemp，报告成了 0600（坑 203）；改用 open() 建临时文件。
  • 结果的打印：设计里没有。一节算完之后打印它的行时出错（形状不同的行）也会丢掉报告，所以打印也包了 try。
  • k 点约化的权重：设计写 “权重从零起累加”。从零起时 −0.0 的权重会变成 +0.0，所以改为从每对第一个点的权重起，与原来的循环完全一样。
  • 确定性检查的算例：check_determinism 的默认算例改在调用时取 DETERMINISM_CASES（原来在定义时取，测试里改它不起作用），空表时不做（_cases([]) 会取全部算例）。
  • time_cu：对每种精度各算一遍，标签从 device 改为 device_float64 等，能量差是 energy_diff_<dtype>（JSON 第 2 版）。k 点线程数从 os.cpu_count() 改为可用的核数。
  • k 点线程的方式用 --workers 个线程，与进程池的进程数相同，便于对照。
  • 工作负载的命令行选项（--dataset、--skdir）没有做：ptbp_workload.calculator 接受 skdir，需要时在脚本里用。
  • 共用 SK 集合与后端：按计划的规则（≥ 0.5% 才做）不做，P129 是 0.06%。
  • 其余按设计：工作负载、四种方式、汇总与流水线的上限、堆叠的分组与守卫、环境的各项、k 点约化的向量化。
