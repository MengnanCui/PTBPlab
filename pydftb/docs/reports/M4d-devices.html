关键信息

pydftb 的 PyTorch 后端现在可以放到 GPU 上：NVIDIA 和 AMD（cuda，AMD 用 ROCm 版 torch）、Apple（mps）、Intel（xpu）。每一步在哪里算由设备的能力决定，CUDA 上自动用确定性算法。新增 GPU 自检脚本 python -m pydftb.validation.gpu_check，由用户在自己的机器上检查正确性并计时。PTBP 新增 --pydftb_backend、--device、--dtype 三个选项。默认仍是 NumPy、CPU、float64，结果逐字节不变。

  • 本机没有 GPU，GPU 上的正确性和速度都“未实测”。在这里做了三项验证：
    • meta 设备检查：把 torch 的默认设备设成 meta（一种不存数据的“空”设备）再计算，凡是没写明设备就新建的张量都落到 meta 上，一与真实数据相遇就报错。这在 CPU 上模拟了“GPU 数据与 CPU 数据混用”的错误。前向计算（M4a）没有这种问题；自动求导（M4b）查出约 50 处，已全部改正，否则在 GPU 上第一次求导就会报错。
    • 退回 CPU 的分支：MPS、XPU 上“部分步骤在 CPU 上算”的布局，在 CPU 上运行时与正常路径逐位相同。
    • 自检脚本本身：在本机 CPU 上跑完全部检查和计时（约 6 分钟）：155 项有判据的检查全部通过，另有 148 项 float32 结果只报告、1 项只对 CUDA；人为制造一处不一致时退出码为 1（测试）。
  • 请用户运行一条命令：python -m pydftb.validation.gpu_check --json gpu_check.json，把 JSON 发回来。里面有正确性结论和三组计时：本征分解网格、按 PTBP 设置计算的 Cu 晶胞、多个结构的矩阵堆成一批。GPU 值不值得用、要不要做跨结构的批量，都看这份数据。
  • PTBP 用 GPU 的规则：DFTB 阶段在主进程里逐个结构计算；与 --optimizer parallel_bo、pso 同用时直接拒绝；梯度优化器（M4c）只用 NumPy 后端；--device auto 在子进程里探测 GPU；plan.json 记下后端、设备、精度和 torch 版本；推荐器发现 GPU 时只打印建议，从不自动改用。
  • 顺带修了自动求导的两处旧错误：没有晶胞的分子带色散时求导崩溃；带色散时 implicit 模式求能量的导数报错。
  • 默认不变：golden 两个环境逐位相同（237 次计算、41,519 个量；最小环境 198 次、36,176 个量）；G1 通过：损失 1.899324742、446.2016018 不变，BO 步的文件与 M4 之前逐字节相同。
  • 未实测GPU 的加速倍数（等用户的自检结果）
  • 155 / 155自检在本机 CPU 上通过的检查
  • 约 50自动求导中改为跟随设备的新建张量
  • 0默认设置下改变的字节

二、怎么用

pydftb

from pydftb import DFTB
calc = DFTB(sk, backend="torch", device="cuda")      # 也可以 "cuda:1"、"xpu"、"auto"
calc = DFTB(sk, backend="torch", device="mps", dtype="float32")   # Apple：只有 float32

from pydftb.ase_calc import PyDFTB
atoms.calc = PyDFTB("skf/", backend="torch", device="auto")

自动求导（pydftb.autodiff）在参数张量所在的设备上算：Params.from_skset(..., device="cuda")。

GPU 自检

python -m pydftb.validation.gpu_check --json gpu_check.json     # 自动选设备，全部检查和计时
python -m pydftb.validation.gpu_check --device cuda:1 --dtype both --json gpu_check.json
python -m pydftb.validation.gpu_check --quick                   # 子集，几分钟
python -m pydftb.validation.gpu_check --device cpu --quick      # 没有 GPU 时检查脚本本身

终端上逐项打印结论，JSON 里是环境、每项检查的数值和结论、全部计时。任何一项正确性检查失败，退出码为 1。

PTBP

ptbp optimize dft/dft.xyz --engine pydftb --pydftb-backend torch --device cuda
ptbp optimize dft/dft.xyz --engine pydftb --pydftb-backend torch --device mps --dtype float32
ptbp plan dft/dft.xyz --engine pydftb --probe        # 有没有 pydftb 能用的 GPU
情况结果
--device 不是 cpu，或 --dtype float32，而后端是 NumPy报错：需要 --pydftb_backend torch（--device auto 也一样，在任何机器上都如此）
--pydftb_backend torch 而引擎是 DFTB+报错：需要 --engine pydftb
--device mps 加 float64报错：MPS 没有 float64，用 --dtype float32
GPU 加 --optimizer parallel_bo 或 pso报错：这两个优化器用多个进程同时算 BO 点，改用 --optimizer bo
梯度优化器加 torch 后端报错：梯度优化器只用 NumPy 后端
--pydftb_backend torch --device auto在子进程里探测，打印选中的设备；没有 GPU 就用 CPU
torch 在 CPU 上与 NumPy 一样多进程并行，每个工作进程 1 个 torch 线程，不用 k 点线程
torch 在 GPU 上DFTB 阶段在主进程里逐个结构算；其它阶段（hotcent 等）照常派生只用 CPU 的子进程

三、设备与能力

设备能力从哪里来精度Cholesky、本征分解float64 数组和求和状态
cpu—float64、float32CPUCPU已验证（M4a、本阶段）
cuda[:i]，NVIDIA视为全部支持float64、float32设备设备代码路径与 CPU 相同；未实测
cuda[:i]，AMD（ROCm）同上，标出 ROCm同上设备设备未实测；批量本征分解的速度取决于 torch 用的求解库，看自检计时
mps，Apple第一次使用时用 2×2 矩阵试只有 float32试得通就在设备上，否则 CPUCPU分支在 CPU 上逐位验证；未实测
xpu，Intel同上试得通 float64 就有试得通就在设备上，否则 CPU没有 float64 时在 CPU同上
  • 两个字段决定布局：linalg_device 是做 Cholesky 和本征分解的设备，precise_device 是存 float64 数组（S 的 Cholesky 因子、布居和能量的双精度求和）的设备。CPU 和 CUDA 上两者就是设备本身，代码路径与 M4a 完全相同，所以数值不变。
  • MPS 的布局：S 在 CPU 上以 float64 分解，L⁻¹ 转成 float32 送到设备；每轮 SCC 的 H′ = L⁻¹HL⁻ᴴ 在设备上算，在 CPU 上做本征分解（如果 MPS 不支持），结果送回设备；密度矩阵、布居、能量的迹在设备上算，求和时送回 CPU 并升到 float64。
  • 为什么用“试一下”而不查表：各版本 torch 在 MPS/XPU 上支持的运算一直在变。试运算的结果按设备缓存，以后 torch 支持了就自动用上。
  • 确定性：CUDA 上有些运算（原子加法、部分 GEMM）每次舍入顺序不同。pydftb 在 CUDA 上计算期间打开 torch 的确定性算法（没有确定性实现的运算只警告），算完恢复用户原来的设置；第一次用 CUDA 前设 CUBLAS_WORKSPACE_CONFIG。自检脚本检查“同一计算两次逐位相同”。GPU 与 CPU 之间不会逐位相同（算法和舍入顺序不同），自检的门槛是 1e-10。

四、没有 GPU 怎么验证

要防的错误在 CPU 上怎么查结果
某个张量建在 CPU 上，与 GPU 上的数据相遇时报错（GPU 上最常见的错误）with torch.device("meta") 下重跑：没写明设备的新张量落到 meta 上，与真实数据相遇就报错；结果必须与普通运行逐位相同前向计算 4 个算例（水、Cu T = 0、CuO 自旋链 k 点、DFTB3 甲醇）原本就没有问题。自动求导 6 个算例 × hf/implicit 两种模式查出约 50 处，改正后全部逐位相同
MPS/XPU 的布局（部分步骤在 CPU 上）算错在 CPU 上强制 linalg_device="cpu"、precise_device="cpu"：数据照样搬运，只是搬到同一个设备5 个算例（含 float32）、3 个算例（MPS 布局，float32）与正常路径逐位相同
能力表、auto、确定性开关的逻辑错误模拟 CUDA、ROCm、MPS、XPU 的可用性和试运算失败选择、报错、警告符合第三节；确定性开关进出后恢复原设置
自检脚本本身的错误gpu_check --device cpu 跑全部检查和计时；人为改动一个结果155 项全部通过；改动后退出码 1、只有那一项失败
PTBP 的 GPU 路径把 is_gpu() 换成真，在 CPU 上走“主进程逐个结构”的路径写出的文件与 torch 串行、4 进程逐字节相同

这些检查不能代替真 GPU：它们保证数据不会放错设备、布局的逻辑正确，但 GPU 上 cuSOLVER、hipSOLVER 等库本身的数值和速度，只有自检脚本在真 GPU 上才测得出。

在 GPU 上怎么读 Cu 表：PTBP 的 DFTB 阶段在 CPU 上是每个核心一个进程同时算，用 GPU 时是主进程逐个结构算。所以 GPU 算一个结构的时间（torch 一列）要小于“NumPy 1 线程”一列除以 CPU 核数，GPU 才比现在的多进程快；多结构堆叠一表的倍数明显大于 1，才值得做跨结构的批量。

六、接入 PTBP

  • 选项：命令行（--pydftb_backend、--device、--dtype；ptbp optimize 和 ptbp plan 用连字符）、YAML（pydftb_backend、device、dtype）、界面（第 6 步“pydftb device”）。默认值不往旧的命令行里加任何东西，默认运行与之前完全相同。
  • DFTB 阶段的进程模型：
    • torch 在 CPU 上：与 NumPy 相同的多进程方案；父进程派生前把 torch 设为单线程（M4a 的规则），每个工作进程 1 个 torch 线程；torch 后端不用 k 点线程。
    • torch 在 GPU 上：1 个工作进程，就是主进程，逐个结构算。用过 CUDA 的进程派生的子进程不能再用 CUDA；PTBP 其它阶段的子进程（hotcent 分片等）只用 CPU，这是常见的做法。自检里有一项专门检查：用过 CUDA 之后派生一个只算 NumPy 的子进程，看它能否正常结束。
  • 计划与建议：
    • ptbp plan 和运行开头的方案多一行“pydftb on torch (cuda, float64; torch 2.14.1)”，plan.json 多一个 backend 字段；用 NumPy 时没有这个字段，文件与之前相同。
    • GPU 时 DFTB 阶段标为“主进程、串行”，不给耗时估计：成本模型只在 CPU 上标定过。torch 在 CPU 上时照常估计，并注明成本模型按 NumPy 标定。
    • 用 NumPy 后端而机器上有 GPU 时，推荐器打印一条建议：先跑自检，再试 --pydftb_backend torch --device auto，并提醒 GPU 是串行地算，只有比 CPU 上的多个进程更快才划算。从不自动改用。

七、发现

  1. 自动求导原本不能在 GPU 上运行。M4b 的代码在 api.py、scc.py、model.py 里用 torch.as_tensor、torch.zeros、torch.eye 新建索引数组、常数和单位矩阵时没有写设备，这些张量总在 CPU 上；参数在 GPU 上时，第一次相遇就报“张量不在同一设备”。M4b 只在 CPU 上测过，所以没发现。现在全部跟随输入的设备，meta 检查覆盖 6 个算例、两种模式。前向计算（M4a 的 Backend 统一经 asarray、index 建张量）没有这个问题。
  2. 自动求导的两处旧错误（与设备无关）。把带色散的算例加进测试时发现：
    • 分子（没有晶胞）带色散时，色散模块照样给出位力（对应变的导数，分子也有定义），代码据此去解晶胞方程，而分子没有晶胞，于是崩溃。现在没有晶胞就不算晶胞导数。
    • 色散作为外部项时，反向传播对不需要导数的输入（implicit 模式求能量时没有应变）也返回了梯度，torch 报错。现在按 needs_input_grad 返回。
    两处都加了测试（hf 与 implicit 的逐项对照新增 2 个色散算例，hf 模式新增一个分子色散算例）。
  3. torch 与 NumPy 在 CPU 上的差别（第五节）：torch 用 MKL，NumPy 用 OpenBLAS，本机都是 4 个线程。本征分解的倍数（NumPy 耗时 / torch 耗时）在 N ≤ 18 时中位数 1.1（0.9–1.7），有快有慢；N ≥ 72 时中位数 2.2（0.7–4.4），complex64 最明显。按 PTBP 设置计算的 Cu 晶胞，torch（4 线程）每轮 SCC 比 NumPy 单线程快 1.04–2.54 倍，与 NumPy 的 4 个 k 点线程相当。但 PTBP 的 DFTB 阶段是每个核心一个进程、每个进程一个线程，比的是单线程对单线程，M4a 在 Cu 数据集上测得 torch 只快约一成。所以在 CPU 上 torch 后端没有理由替代 NumPy。
  4. 比较速度要用 PTBP 的求解器。DFTB 类的默认求解器是逐个 k 点调 SciPy 的 eigh（参考实现），PyDFTB 和 PTBP 用的是 batched。自检的 Cu 计时起初用了前者，k 点线程因此完全不起作用（SciPy 的 eigh 不释放 GIL，M3a 已知），Cu₄ 上 4 个线程反而慢 1.5 倍；改用 batched 后，k 点线程在 4 原子以上的晶胞快 1.7–2.3 倍（1、2 原子的晶胞矩阵太小，只快 1.1–1.3 倍）。另外，求解器不同，T = 0 金属的 SCC 轮数也会不同（Cu₄：eigh 42 轮，batched 28 轮，torch 37 轮），所以比较耗时也要看每轮。
  5. T = 0 的 32 原子 Cu 晶胞 1000 轮也不收敛（3×3×3 k 点，|dq| 停在 1.6e-2），完整自检的 30 分钟里它占了 24 分钟。计时因此最多算 100 轮，按每轮耗时比较；PTBP 的数据集是小晶胞加 k 点，不受影响。
  6. CPU 上把多个结构堆成一批做本征分解没有好处（0.90–1.02 倍）。在 GPU 上，小矩阵的批量越大越能填满设备，结果可能完全不同；这正是自检要测的。
  7. float32 的 SCC 容差不能太小。自检起初用 1e-6：74 个参考中有 3 个（DFTB3 的 Cu₄CO、带 f 轨道的 GdO₂ 分子、带 onsite 修正的 DFTB3 水）在 float32 下残差降不到 1e-6，Broyden 混合随后发散（|dq| 到 1e3），500 轮后能量差到 47 Ha。用 M4a 的 1e-5 时，这 3 个分别在 14、9、7 轮收敛（DFTB+ 19、9、8 轮）。自检的 float32 部分因此用 1e-5，只报告、不判定。另外，T = 0 的金属在 float32 下费米能级搜索可能失败（M4a 已知），测试里的 float32 算例用有展宽的 Cu₈。

九、与计划的偏差

  • D4（机器指纹加入 torch）没有做。指纹只用来缓存 NumPy 的速度探测，torch 的版本不影响它；等有了 torch 自己的探测再加。
  • 多做了自动求导的设备改造（第七节第 1 条）。计划只写了“设备选项”，没想到 M4b 的代码在 GPU 上会出错；meta 检查查出后一并改了。
  • 梯度优化器只支持 NumPy 后端。自动求导本身已能在设备上算（自检检查 hf 与 implicit 一致、与 CPU 一致），但 PTBP 的梯度流程（M4c）只在 NumPy 引擎上验证过。
  • MPS 选 float64 在 PTBP 开头就报错，不等到第一次 DFTB 计算；界面选 mps 时直接写 float32（MPS 没有别的选择）。
  • 自检的 float32 部分只报告，SCC 容差用 M4a 的 1e-5（1e-6 时有 3 个算例发散，第七节）。
  • Cu 计时最多算 100 轮 SCC，并给出每轮耗时：计划没有考虑 T = 0 的大晶胞不收敛（第七节）。
