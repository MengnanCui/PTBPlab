关键信息

周期体系的 Coulomb（Ewald）在大体系上不再存原子对表。估计的实空间原子对超过 600 万（约 500 个水分子）时，Coulomb 按中心原子分块：每块现算自己的原子对（新的 neighbors.pair_blocks），把 γ、力与位力的贡献加上去就丢掉；倒空间的和按 G 分块，γ 原地累加。DFTB+ 也是这样做的（它的 TDynNeighList 不存对表）。小体系照原来的代码走，逐位不变；分块的结果对原路径到舍入。没有新的用户选项。顺带修了 M7d 的一个问题：主进程被杀之后，工作进程不会自己退出。

  • 精度：强制分块对原路径，6 个冻结的周期算例（Γ 点与 k 点、f 壳层、DFTB3、H 阻尼、H5、点电荷）加上 CuO 链上的两个壳层分辨变体（一个带 DFTB3），SCC 轮数全部相同，能量差 ≤ 3.6e-14 Ha，电荷 ≤ 7.6e-14 e，力 ≤ 1.7e-14 Ha/Bohr，应力 ≤ 3.0e-17（P128）。实空间部分逐位相同，块的大小不改变任何一位。1728 个水分子的 SCC 加力对原来的 Coulomb：能量差 9.1e-13 Ha，电荷 2.5e-12 e，力 2.8e-13 Ha/Bohr。
  • 内存与时间（1728 个水分子，SCC 加力，Subsystems(processes=4)）：主进程峰值从 9.74 GiB 降到 2.06 GiB，建立 Coulomb 从 60 s 降到 23 s，全程从 216 s 降到 172 s。
  • 阈值附近（只算 Coulomb，建立加一次带位力的力，P126c）：216 个水分子时原路径快（1.4 s 对 1.9 s），343 个时相当（3.6 s 对 3.8 s），512 个时分块快 11%（6.5 s 对 7.2 s），1000 个时快 33%（18.0 s 对 26.7 s）。分块的峰值一直是 0.14–0.20 GiB，原路径是 0.33、0.65、1.18、3.22 GiB。阈值 600 万对落在 512 个水分子附近。
  • 更大的体系：4913 个水分子（14739 个原子）用 M7c 的稀疏路径 SCC 加力 1281 s，主进程峰值 5.73 GiB，在这台机器给作业的 13.36 GiB 之内；原来的代码单是对表就要约 13 GiB，建立时约 45 GiB。4096 个水分子用分治、4 个进程 558 s，整台机器 12.6 GiB。
  • 还放不下的：4913 个水分子用分治（4 个进程）仍超出 13.36 GiB，原因在 M7d：子体系在图样上的索引（1.99 GiB）经 fork 在每个工作进程里留着整份（共用的页），工作进程还各有本征矢与图样数组的副本（第五节）。γ 本身（N²，4913 个水分子 1.62 GiB）与 SK 原子对的整张邻居表（建立时临时多出 3.86 GiB）也还在。
  • 9.74 → 2.061728 个水分子主进程的峰值（GiB）
  • ≤ 3.6e-14分块对原路径的能量差（Ha，8 个周期算例）

开发细节一、做了什么
位置内容
neighbors.pyneighbor_list 拆成 _image_tree（像的范围与全部像的 k-d 树）与 _central_pairs（一段中心原子的稀疏距离查询、pair_vectors、去掉零距离、按 (i, j, 像) 排序），只是搬代码，结果逐位不变。新的 pair_blocks(pos, cell, pbc, cutoff, step) 每次给出一段中心原子 [lo, hi) 的 (lo, hi, i, j, 像, 矢量, 距离)，像的 k-d 树只建一次；拼起来就是 neighbor_list。
coulomb.py
  • 模块常数 PAIR_TABLE_LIMIT = 6_000_000、BLOCK_PAIRS = 2**19、G_CHUNK = 1024、ROW_BLOCK = 1024。
  • __init__：周期体系用 N²·(4/3)π·rc3/V 估计实空间的原子对（rc 是短程与 Ewald 截断的较大者），超过阈值时记下 _step（每块的中心原子数，使每块约 BLOCK_PAIRS 对），nl 与 sp_* 设为 None；否则照旧。
  • 位点展开与 S（含 H 阻尼与 H5）改为对给定数组的函数 _site_pairs_of、_short_of，原来的 _site_pairs、_sp_short 包一层，逐位不变；_blocks() 逐块给出原子对与它们的位点对。
  • _matrix_blocks()：同一原子的 γ0 只放在同一原子的元上；每块 np.add.at 加上 −S 与 erfc(αd)/d；倒空间每 G_CHUNK 个 G、每 ROW_BLOCK 行一次 GEMM，原地加；每个原子一个位点时 Ewald 部分直接加进 γ，只有一个 N × N 数组，壳层分辨时先加进原子级的矩阵，再按行块展开到位点。
  • _gradient_blocks()：倒空间按 G 分块，grad = zeros; grad += … 的次序照旧；再逐块算 dedr（短程与 Ewald 在同一个数组里）并 np.add.at(grad, i, …)；位力的对的部分从第一块起累加（不从零开始，对称晶胞里不翻出 −0.0），最后加 G 的各项。
thirdorder.pyc.nl 为 None 时，按 min(rc, 表中最大的截断) 逐块取对，按原来的条件过滤再拼起来，存为自己的 nl（与过滤整表的结果逐位相同）。
autodiff/model.pygamma_matrix 遇到分块的 Coulomb 时抛出 NotImplementedError，说明对数超过了 coulomb.PAIR_TABLE_LIMIT。
perfmodel.pypydftb 的内存估计里，周期体系的 Coulomb 原子对与位点对两项在阈值处封顶（分子总存表，不封顶；PTBP 用它安排进程）。
subsystems.pyfork 出来的工作进程先关掉继承来的主进程那一端的管道，recv() 遇到 EOFError 就退出。以前主进程被杀（P124 里 4913 个水分子超出内存）之后，工作进程收不到 EOF，一直留着。
测试新文件 tests/test_coulomb_chunks.py（21 项，第六节）；tests/test_subsystems.py 多一项（工作进程随主进程退出）。

二、怎么用

  • 不用做什么：周期体系的实空间原子对估计超过 600 万时自动分块，结果与原路径到舍入相同（第三节）。分子与小晶胞照原来的代码走。
  • 模块常数（写法同 hybrid.IMAGE_CHUNK）：pydftb.coulomb.PAIR_TABLE_LIMIT、BLOCK_PAIRS、G_CHUNK、ROW_BLOCK。测试用 monkeypatch 把阈值设为 0、把块设小来强制分块；设为 float("inf") 就总存表。
  • 分块时：Coulomb.nl 与 sp_pair、sp_a、sp_b、sp_d 是 None，不会给出一张不完整的表；γ、gradient（力、位力、双线性的 other）照常。
  • 能用的：Coulomb 与求解器无关，所有求解器都能用（测过本征分解、分治与稀疏路径）；Γ 点与 k 点、DFTB3（ThirdOrder 自己逐块取对）、H 阻尼、H5、壳层分辨、点电荷、应力、ASE 的 MD（都在第三节的核对里）；torch 后端的前向计算也照常，它的 γ 与力本来就由 NumPy 的 Coulomb 算。
  • 报错的：autodiff（pydftb.autodiff，PTBP 的梯度）要整个 Ewald 范围的对表，遇到分块的 Coulomb 抛出 NotImplementedError；600 万对以下照旧。

四、速度与内存

本机 4 核，作业的内存上限 13.36 GiB（cgroup），M7c 的水盒子（约 1 g/cm³，ptbp_hcocu，每个原子一个位点）。

阈值附近（P126c）：只建 Coulomb 并算一次带位力的 gradient（随机电荷），每个配置一个新进程，三次取最短；峰值是 tracemalloc 的（NumPy 的数组，不含 cKDTree 的 C++ 缓冲）。

五、五千个水分子

计划的目标是本机跑完约 5000 个水分子的 SCC 加力。4913 个水分子（173，14739 个原子，29478 个轨道）：

  • 稀疏路径（M7c，截断 1e-6）：1281 s，16 轮，主进程峰值 5.73 GiB（P126）。每块 39 个中心原子，实空间约 1.95 亿对：原来的代码单是对表就要约 13 GiB，建立时约 45 GiB。
  • 分治（M7d，4 个进程）：超出 13.36 GiB，被系统杀掉（P124，原型）。当时主进程常驻 5.96 GiB，四个工作进程的常驻内存各约 5.7 GiB，其中大部分是从主进程继承、共用的页。

顺带修的：OOM 之后四个工作进程没有退出（父进程变成 1 号进程），要手工杀掉。原因是 fork 的工作进程继承了主进程那一端的管道，主进程死了它们也收不到 EOF。现在工作进程启动时关掉这些端，recv() 遇到 EOFError 就退出；测试 test_workers_exit_with_the_master 用 SIGKILL 杀掉一个起了三个工作进程的子进程，三个工作进程都在 30 s 内退出。

六、测试与门槛

tests/test_coulomb_chunks.py（21 项）：

  • 块的查询：pair_blocks 拼起来等于 neighbor_list（斜晶胞、晶胞外的原子，块为 1、7、1000 个原子）。
  • γ、梯度与位力：40 个原子的斜晶胞（两位点的原子、H 阻尼）强制分块对存表，有无 other；一块与多块逐位相同；分子不分块。
  • ThirdOrder：建在分块 Coulomb 上的对表与 Γ3 逐位相同。
  • 整个计算：第三节的 8 个算例（并断言分块路径确实运行了）；ASE 的两步速度 Verlet（三个几何都走分块）；torch 后端的 water_box_gamma 与 water_box_dftb3。
  • 内存守卫：216 个水分子的 tracemalloc 峰值，存表时大于 100 MB，分块时小于 3 倍的 γ 加 40 MB。
  • autodiff 的拒绝；perfmodel 的封顶（周期体系封顶；分子与 DFTB+ 不封顶）。

七、与设计的偏差

  • 阈值：设计写 “由 P124 定，约 4M–8M 对”。定为 600 万对，依据是 P126c：两条路径的时间在 343–512 个水分子之间交叉，原路径在 512 个水分子（6.5M 对）建立时的峰值约 1.2 GiB。
  • 壳层分辨的测试：设计列了 cu4co_shell_resolved 与 cu4co_dftb3_shell，但它们是分子，总走原路径，什么也测不到（P128 第一遍两者的差都是 0）。改为在周期的 CuO 链上打开 shell_resolved（另一个加上逐壳层的 DFTB3），并在测试里断言分块路径确实运行了。
  • torch 后端：设计写 “torch 后端照旧走原来的整块对表”。实际上 Coulomb 总是 NumPy 的对象，torch 后端的前向计算只取它的 γ 与力，所以大体系上同样分块，结果到舍入相同（测试 test_torch_backend_on_blocks）；只有 autodiff 要对表而拒绝。
  • perfmodel：设计只写了 Coulomb 原子对一项封顶。分块时位点对也不存，所以位点对一项按同样的比例封顶；分子总存表，不封顶。
  • 工作进程的退出：设计里没有。P124 的 OOM 之后发现，修复并加了测试（第五节）。
  • 块的大小：原型按固定的 64 个中心原子分块，实现按每块约 219 对定（1728 个水分子时 66 个原子），两者在 1728 个水分子上逐位相同。
  • 内存的量法：VmHWM 在分配器复用前面释放的页时量不出分块路径的小峰值（P126 的 512 个水分子量出 0.007 GiB），阈值附近的比较改用 tracemalloc（P126c），它看不到 cKDTree 的 C++ 缓冲，大体系仍用 VmHWM 与整台机器的采样。
  • 其余按设计：块的查询、逐位相同的条件、带符号的零、G 分块、ThirdOrder、autodiff 的拒绝、模块常数、没有新的用户选项。

八、下一步

  • M7e：GPU 自检与跨结构批量（路线图的下一块）。GPU 自检要在有 GPU 的机器上运行 pydftb gpu-check --dtype both --json gpu_check.json，再把 JSON 发回来。
  • 分治的内存（M7d 的后续，可以做成一小块）：子体系的索引改用 int32 的位置、核心部分用掩码，约省一半；每个工作进程只建自己那些子体系的索引（MPI 的进程已经这样）；工作进程只收发自己用到的图样元。目标是 4913 个水分子在 4 个进程下放得下，要实测。
  • SK 原子对分块：build_pairs 仍建整张邻居表，4913 个水分子时建立阶段临时多出 3.86 GiB，是现在最大的临时峰值。
  • 不建 γ：γ 本身是 N²（4913 个水分子 1.62 GiB，一万个 6.7 GiB）。再往上要每轮 SCC 用结构因子算倒空间的电势、按块算实空间的电势，力也一样；这改变 SCC 的每一轮。ThirdOrder 的 Γ3、LJ 与 Slater–Kirkwood 色散的 N × N 参数矩阵、点电荷与 ESP 的 cos/sin 也是 N 的平方。
