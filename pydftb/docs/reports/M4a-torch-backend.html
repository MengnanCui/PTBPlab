关键信息

DFTB(backend="torch", device=..., dtype=...)（PyDFTB、pydftb.SCC 同名选项）把每轮 SCC 中最重的部分放到 PyTorch 上：k 点折叠、Cholesky、本征分解、密度矩阵、Mulliken 布居、能量的迹和力用到的实空间密度。几何、参数、γ、混合器和费米能级搜索仍是 NumPy。默认仍是 NumPy，NumPy 路径与 M4 之前逐字节相同。

  • 与 DFTB+ 对照：torch 后端用原来的容差通过全部 74 个单点参考（每个算例的 SCC 轮数与 DFTB+ 相同）和 11 个优化/MD 参考。
  • 与 NumPy 对照（float64，SCC 收敛到 1e-12，74 个算例中的最大差）：能量 3.6e-14 Ha、力 4.1e-14 Ha/Bohr、电荷 1.4e-13 e、本征值 2.4e-14 Ha，SCC 轮数全部相同。两者用的是不同的 LAPACK（MKL 与 OpenBLAS），所以不逐位相同，但差别只在最后两三位。
  • float32：最大差能量 4.3e-6 Ha、力 1.6e-6 Ha/Bohr、电荷 9.4e-6 e；只报告，不作承诺。
  • 速度（这台 4 核 CPU，单进程）：PTBP 的 Cu 数据集（66 个结构，PTBP 的 k 点规则和设置）在一个进程里算能量和力：NumPy 28.8 s，torch float64 25.7 s（快 11%），float32 24.3 s；4 个线程几乎不再变快（矩阵只有 9–18 阶）。M3a 的 4 个进程只要 7.8 s，所以 torch 在 CPU 上不能代替多进程，它的意义在 GPU（未实测）和 M4b 的自动求导。
  • 发现的坑：threadpoolctl 把 torch 的 OpenMP 线程数改成 1 时，torch 静态链接的 MKL 仍按原来的线程数开并行区；在多线程跑过 torch 的父进程 fork 出的子进程里，这会让子进程卡死。现在 pydftb 总是用 torch.set_num_threads 设线程数（第六节）。
  • 74 + 11DFTB+ 参考在 torch 后端上全部通过
  • ≤ 1.4e-13torch 与 NumPy 的最大差（float64）
  • 0NumPy 路径改变的位（golden 237 次计算、41,519 个量）

二、结果是否与原来相同

  • pydftb 的 NumPy 路径：golden 工具与 M4 之前的提交 65115d1 比较。conda 环境 237 次计算（74 个参考 × 三种求解器设置、11 个动力学参考的前几步、PTBP 设置下的 4 个 Cu 晶胞）、41,519 个量，最小环境 198 次（D3/D4 算例跳过）、36,176 个量，全部逐字节相同。唯一新增的是 _Setup.dev 字段（NumPy 下为 None）。
  • PTBP：tools/engine_parity.py 在已发表的 Cu 点（r0_w 2.749、r0_d 12.036 Bohr）跑一个 BO 步，与基准提交 65115d1 的运行逐字节比较：energygeometry 模式 17 个文件、dataset 模式 8 个文件（SKF、dft_final.xyz、dftb_full.xyz、状态方程的轨迹、log.out、par.out 等）全部相同，损失 1.89932474214 和 446.20160183606 不变；工作区内 1 核与 4 核逐字节相同。
  • import pydftb 和 NumPy 后端的计算不导入 torch（有测试）。

三、torch 与 NumPy、与 DFTB+ 的对照

1. 与 DFTB+ 的冻结参考

refgen --check --backend torch：74 个单点参考全部通过（原来的容差：能量、力、电荷 1e-6，应力 1e-7，本征值 1e-8），每个算例的 SCC 轮数与 DFTB+ 相同；与 DFTB+ 的偏差和 NumPy 后端同一量级。dynamics --check --backend torch：7 个优化、4 段 MD 全部通过（能量差 ≤ 1.1e-8 Ha，位置差 ≤ 2.2e-6 Å）。

四、性能

1. 本征问题（探测，一个线程）

随机厄米 H、κ(S) ≈ 10 的堆叠：torch 与 NumPy 的本征值相对差 ~1e-15、密度矩阵 ~1e-14，与 NumPy 自己两种算法（批量与 SciPy gvd）的差同一量级；耗时相当，k 点堆叠上 torch 快 10–25%（N = 18、1,688 个 k 点：117 ms 对 133 ms）。详表见设计文档第四节。

2. PTBP 的 Cu 数据集，一个进程

66 个结构（1–2 个原子，k 点 1–2,048 个，共 50,081 个不可约 k 点），已发表的 Cu 点上 PTBP 自己生成的表，PTBP 的 pydftb 设置（T ≈ 0、SCC 容差 1e-5、0.01 Bohr 差分），每个结构一次能量加力：

线程NumPytorch float64torch float32float64 与 NumPy 的最大差
128.8 s25.7 s24.3 s能量 1.3e-9 eV、力 4.8e-9 eV/Å；SCC 共 443 轮，两边相同
427.2 s25.1 s22.7 s

与 M3a 的多进程比较：同一个 DFTB 阶段 4 个进程 7.8 s。torch 在 CPU 上单进程只快 1 成左右，不改变 PTBP 的并行方式（M4d 才把它接进 PTBP，并在 GPU 上进程内运行）。这里差别在 1e-9 量级而不是第三节的 1e-14，是因为 SCC 只收敛到 1e-5，两边的舍入差被 SCC 放大到这个容差以内。

T ≈ 0 时 kT = 1e-8 Ha，float32 的本征值误差（~1e-7 Ha）比 kT 大，费米能级附近的能级占据数在 0 和 1 之间乱跳：能量几乎不受影响，个别结构的力差到 3e-2 eV/Å。加展宽后正常。结论：float32 不要用于 T ≈ 0 的金属的力。

五、单元测试

M4a 新增 98 个测试项：test_torch_backend.py 23 个（12 个算例的 float64 对照、4 个 float32、结果类型、选项检查、NumPy 下转换是原样返回、ASE 接口与线程数恢复、沿用电荷、fork 后不卡死、命名空间分派），test_import_hygiene.py 1 个，test_reference.py 按后端参数化后新增的 74 个。conda 环境（有 torch、DFTB+、dftd3/dftd4）：pydftb 369 个全部通过；最小环境（CI，无 torch）：256 个通过、91 个跳过（torch 的 74 + 1、没有 dftd3/dftd4 的 16）；最小环境加 torch：339 个通过、30 个跳过（没有 dftd3/dftd4）。PTBP 的 179 个测试中，除 7 个已知失败的界面冒烟测试和 1 个跳过外全部通过（与之前相同）。

六、发现的问题

  • threadpoolctl 管不到 torch 的 MKL，fork 后会卡死。torch 的 CPU 版静态链接 MKL，threadpoolctl 只能改 OpenMP 的线程数。PyDFTB(threads=1) 原来先进入 threadpoolctl 的 threadpool_limits(1)，于是 torch.get_num_threads() 读到 1，pydftb 就没有再调用 torch.set_num_threads(1)；MKL 仍按 4 个线程开 OpenMP 并行区。父进程用 4 个线程跑过 torch 后 fork 出的子进程，就卡在第一个复数矩阵乘法里（测试超时）。改为：总是调用 torch.set_num_threads（它同时设 MKL 的线程数），并且先于 threadpoolctl 读取原来的值。现在有测试：父进程用 4 个线程算过之后 fork 3 个子进程，各自用 1 个线程算同一个结构，结果与父进程一致。
  • fork 的规则（探测）：父进程跑过多线程的 torch 并行区之后，子进程只要在任何 torch 运算之前把线程数设好，就能正常运行；不设则 4 个子进程全部卡死。PTBP 接入 torch 时（M4c、M4d），工作进程在开始计算前先设线程数。
  • ops.namespace() 自 M0 起没有被调用过；M4a 起它真正按输入类型分派，M4b 的核函数将用它。
  • li2_sk_tail 在 SCC 容差 1e-12 下 500 轮不收敛（两个后端完全相同；原来的 1e-10 容差下 1 轮就满足），与后端无关，只在对照时用了更紧的容差才显现。
  • T ≈ 0、只用 Γ 点的单原子 Cu 晶胞，费米能级搜索可能失败（与 M4 无关，M4 之前的提交相同）：用测试参数 ptbp_hcocu 时，Cu 数据集的第 44、55 个结构若按各自的玻尔兹曼权重只用 Γ 点，会报 “Fermi level search did not converge”。半满的简并能级要在 kT = 1e-8 Ha 下把电子数配到 1e-7 以内，μ 的浮点精度不够。DFTB+ 是同一个算法、同一个容差（etemp.F90:178），也会报错。PTBP 按状态方程组中心结构的权重给 k 点，这两个结构用的是 k 网格，实际运行不受影响。
  • float32 不适合 T ≈ 0 的金属的力：见第四节第 3 小节。

七、与计划的偏差

  • 能带和 DOS 没有改成报错：bands.eigenstates 本来就在主机上用 NumPy 求解冻结电荷下的本征态，torch 引擎得到的电荷可以直接用，结果与 DFTB+ 的参考一致（参考测试中的能带算例在 torch 后端上也通过）。
  • torch_xp 只保留了本阶段用到的三个函数；其余在 M4b 用到时再加。
  • TorchSolver 放在 pydftb/backend/，solver="eigh" 和 "batched" 在 torch 后端下都用它。
