关键信息

4913 个水分子（14739 个原子）用分治、4 个进程的 SCC 加力现在放得下：全部进程的物理占用合计峰值 10.88 GiB，在 M7d2 被系统杀掉的 13.36 GiB 之内；合计峰值从 15.23 GiB 降到 10.88 GiB，时间从 1308 s 降到 857 s。结果对 M7d2 逐位相同，没有新的用户选项。改的是 M7d2 报告第八节列出的三处：子体系的索引（每个图样元 40 → 9 字节，由工作进程自己建）、工作进程收发的数据（只有自己用到的图样元，空间上连续的分配）、SK 原子对的建立（按块写进最终的数组）。

  • 逐位相同：1728 与 4913 个水分子的能量、电荷、力对 M7d2 的代码逐位相同；build_pairs 的 12 个数组在各种块大小下逐位相同（水、Cu、CO、SelectedShells，无导数、复数步长、有限差分）；1、2、4 个工作进程与 MPI 的 3 个进程都等于单进程。
  • 4913 个水分子（4 个进程，同一台机器、同一口径）：合计峰值 15.23 → 10.88 GiB，主进程 5.86 → 4.99 GiB（VmHWM 8.24 → 5.53 GiB），最大的工作进程 2.84 → 1.68 GiB；本征分解 545 → 331 s，密度 314 → 113 s（工作进程收发的数据少了）。M7d2 的 15.23 GiB 超过 13.36 GiB，与当时被杀相符。
  • 1728 个水分子（同一台机器、同一口径）：合计峰值 3.58 → 3.20 GiB，最大的工作进程 0.87 → 0.61 GiB，全程 263 → 205 s。
  • SK 原子对：建立时的临时峰值不是邻居表（1728 个水分子只有 0.22 GiB），而是 SKTable.evaluate 为整组原子对取出的样条系数（每对约 1.3 kB）。按块（至多 214 对）之后，1728 个水分子带导数的临时峰值 0.94 → 0.06 GiB，时间 20.7 → 14.6 s。
  • 还在的：γ（N × N，4913 个水分子 1.62 GiB）、工作进程里的本征矢；再往上要不建 γ 的 SCC 电势（第八节）。

一、改了什么

  • subsystems.py：
    • _index：存 lin（子体系块里的平铺位置）、g（图样位置）、nk、both；p > 0 的元在前，不再复制；放得下时用 int32。
    • _Workers(groups, pattern_args)：每个工作进程拿到自己的（核心、子体系原子）与图样，fork 之后自己建索引，发回用到的图样元 used；出错时主进程关掉全部工作进程，抛出 RuntimeError("a subsystem worker failed: …")。
    • set_overlap、eig 只发 s[used]、h[used]，density 只回这些元，主进程 rho[ik, used] += part。MPI 改用 scatter，协议相同。
    • _assign：子体系不少于 8 × 进程数时，按代价 m3 的累加和把连续的核心（格子的次序）切成等代价的段；否则照旧“最大的先给最空的”。
  • hamiltonian.build_pairs：先分组、算出元的总数，分配最终的 rows、cols、pair_of、h、s、dh、ds，再按块（PAIR_CHUNK_PAIRS = 214 对、PAIR_CHUNK_ELEMENTS = 218 个元）填进去；块至少两对。PairBlocks 的字段与类型不变。

二、怎么用

没有新的选项，照旧：

DFTB(sk, scc=True, solver=Subsystems(buffer=6.0, core=6.0, processes=4))

MPI 照旧是 mpiexec -n N python -m pydftb.subsystems run.py。

三、逐位相同

  • 整个计算（M7d2 的提交 c1a11bd 的冻结副本对本次的代码，同一个解释器，水盒子 bench.systems.water_box，ptbp_hcocu 的 H s、O sp，SCC 加力，scc_tol 1e-7，Γ 点，缓冲与核心 6 Å，4 个进程）：216、1728、4913 个水分子的能量、电荷与力的字节都相同，SCC 轮数相同（15、16、16）。
  • 进程数：27 个水分子 1、2、4 个工作进程（2 个走连续分配，4 个走“最大的先”）与 216 个水分子 4 个进程都等于单进程；MPI 3 个进程（MPICH 4.3、mpi4py 4.1）等于单进程。
  • SK 原子对：五组设置（水 27 个分子、Cu fcc 32 个原子、CO 分子、SelectedShells 的水分子；无导数、复数步长、有限差分 1e-4 Bohr）在每块 1–214 对、1–218 个元的各种组合下，12 个数组与原来的字节相同。

四、内存与时间

这台机器是 macOS、32 GB、10 核。内存用每个进程的物理占用（ri_phys_footprint：fork 继承而没有改写的页只算在主进程上），每 0.5 s 采样，“合计”是各进程同时刻之和的最大值；另列主进程的 VmHWM 以便与 M7d2 的数比较。两边都在机器空闲时运行。

  • 求解快了：本征分解与密度每轮都要把 H 发给工作进程、把 P、W 收回来。原来每个进程收发整个图样（4913 个水分子每个数组 0.10 GiB，P 与 W 各一份，四个进程），现在只有自己用到的那一段。密度一步快 2.0–2.8 倍，本征分解快 1.3–1.6 倍。
  • 工作进程：4913 个水分子时每个 1.53–1.68 GiB（原来 2.46–2.84 GiB），其中本征矢约 0.5 GiB（M7d2 第五节：全部子体系合计 1.92 GiB），其余是自己那些子体系的索引、S、H、P、W 的局部副本与子体系的临时数组。
  • 主进程：1728 个水分子时物理占用比原来略高（0.95 → 1.09 GiB），是给每个工作进程切出 s[used]、h[used] 的临时数组；4913 个水分子时 VmHWM 从 8.24 降到 5.53 GiB，因为主进程不再为全部子体系建索引（M7d2 第五节：1.99 GiB），SK 原子对的临时峰值也没有了。
  • 每个工作进程用到的图样元：216 个水分子、缓冲与核心 3 Å、4 个进程时每个都少于图样的 80%（测试的门槛）。

  • 邻居表本身很小：1728 个水分子 119 万对，保留 0.080、峰值 0.219 GiB。M7d2 报告把建立阶段的临时峰值（4913 个水分子 3.86 GiB）归给了“整张邻居表”，这是错的。
  • 大头是 SKTable.evaluate 的 coef[ii]：每对 (8, 20) 个 float64，每个文件一次（A–B 与 B–A），复数步长时每个分量再来一遍；以前一次取一整组（如所有 H–H 对）。只按元数分块不够：H–H 每对一个元，一块仍有 26 万对。
  • 块至少两对：一对的块让复数步长的 dh 在最后一位不同（≤ 2.8e-17，numpy 的堆叠 matmul 在批量为一时走另一条路）；两对以上的任何块都相同。

六、测试与门槛

tests/test_dc_memory.py（12 项）：紧凑索引对 M7d 的索引（元集合、分区权重、稠密块、密度贡献逐位相同）；used 的下标；连续分配；216 个水分子 4 个进程只用部分图样且结果逐位相同；工作进程出错时报错；build_pairs 在 5 种块大小下逐位相同（水与 Cu × 三种导数，6 项）；分子与没有原子对的情况。test_subsystems.py：test_processes_give_the_same_bits 多一个 4 个进程；test_workers_exit_with_the_master 改用新的 _Workers 参数，没有 /proc 时用 os.kill(pid, 0)，在 macOS 上也运行了。

七、与设计的偏差

  • SK 原子对的原因：M7d2 的计划是“SK 原子对分块”，以为要分块的是邻居表；探针（第五节）表明是样条系数，所以按对数封顶，邻居表照旧一次建好（它也是 PairBlocks 的字段）。
  • 量法：M7d2 在 Linux 上用 smaps_rollup 与 MemAvailable；这台机器是 macOS，psutil 读不到子进程的 USS，RSS 与“已用”不可靠，改用物理占用（设计第二节）。所以 4913 个水分子的“合计”与 M7d2 的“整台机器”不完全是同一个量，对比用同一台机器上两份代码的同一口径。
  • 4913 个水分子在哪里跑：M7d2 的 OOM 发生在 13.36 GiB 的作业上限下；这里的机器有 32 GB，原来的代码也能跑完，合计峰值 15.23 GiB（超过 13.36 GiB）。“放得下”是指新代码的合计峰值 10.88 GiB 小于 13.36 GiB，没有在那台机器上重跑。
  • 其余按设计。

八、下一步

  • 不建 γ：γ 是 N × N（4913 个水分子 1.62 GiB，一万个 6.7 GiB）。再往上要每轮 SCC 用结构因子算倒空间的电势、按块算实空间的电势，力也一样；ThirdOrder 的 Γ3、色散的参数矩阵、点电荷与 ESP 的 cos/sin 也是 N 的平方。
  • 工作进程的本征矢：只需要占据的态，但化学势要等所有子体系的本征值才知道；可以先发回本征值、定下 μ，再只留 f > 0 的列（多一次通信），省下约三分之一。
  • 测试环境：test_mpi_ranks_give_the_same_bits 的参考也应在一个 BLAS 线程下算；本机 test_kthreads 的两项失败另查。
  • M7e-2：等 GPU 自检的 JSON。
