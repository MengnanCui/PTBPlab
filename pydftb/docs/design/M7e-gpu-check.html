关键信息

路线图上的 M7e 是“GPU 自检与跨结构批量”。本机没有 GPU，M4d 在 CPU 上量到把 32 个结构的 k 点矩阵堆成一批只快 0.90–1.02 倍，并说要等用户 GPU 上的自检数据再决定跨结构批量。所以 M7e 先做不需要 GPU 的部分：修好 GPU 自检，让它在用户的 NVIDIA GPU 上跑一次，就能回答跨结构批量值不值得做。同步 SCC 的跨结构批量（M7e-2）等这份 JSON 再定。

  • 自检现在的问题：
    • JSON 只在全部跑完后才写，任何一项出错就什么都不留。
    • 堆叠的计时只算 eigh，而且总用 complex128 的随机矩阵：在 MPS 上会崩，在 CUDA 上也只量到一小部分工作。
    • --dtype both 不影响计时。
    • CUDA 在 CUBLAS_WORKSPACE_CONFIG 设好之前就被启动了。
  • 决定性的数（P129，PTBP 的 Cu 数据集 66 个结构，单线程）：
    • 整个 DFTB 阶段 26.2 s。
    • torch 后端只把 SCC 的线性代数放到设备上，留在 CPU 的工作有 14.4 s（55%）：γ（Ewald）6.2 s、费米能级 2.4 s、力 3.2 s、原子对 1.8 s 等。
    • 单是这部分，就比 4 个进程的整个阶段（理想情况 26.2 / 4 = 6.6 s）长一倍多。GPU 的数字要连同这部分一起读。
  • 共用 SK 集合与后端不做：每个结构重建 ParamSet 与 SKSet 合计只占阶段的 0.06%，低于计划定的 0.5% 门槛；SKF 的文本已按进程缓存。
  • k 点的时间反演约化占 0.70%（每个 16³ 网格约 10 ms），高于门槛：把 kpoints.reduce_time_reversal 改成向量化，结果逐位不变。
  • 同步效率（P130）：SCC 每个结构 5–8 轮，按 N 与实/复分组后 Σn / (S·max n) = 0.86–0.90，所以同步 SCC 本身不浪费多少。
  • 55%torch 路径里留在 CPU 的工作（P129）
  • 0.06%共用 SK 集合能省的（不做）
  • 0.86–0.90同步 SCC 的效率（P130）
  • 1 次用户在 CUDA 上要跑的自检

一、范围

  • 做：
    • GPU 自检总能写出 JSON；计时照 --dtype；记下判断所需的环境。
    • 新的工作负载 validation/ptbp_workload.py：不用数据文件造出 PTBP 的 Cu DFTB 阶段。
    • 新的计时：PTBP 阶段逐个结构在 GPU 与 CPU（单线程、k 点线程、进程池）上的时间；完整一轮求解在堆叠与逐个时的时间。
    • reduce_time_reversal 向量化。
  • 不做：
    • 同步 SCC 的跨结构批量与相应的 API（M7e-2，等 JSON）；
    • 共用 SK 集合与后端（P129：0.06%）；
    • 省掉 PTBP 用不到的应力：PTBP 把它写进了 dftb_band.xyz，文件会变（P129：0.8%）；
    • 把 γ、原子对、费米能级等搬到 GPU 上（M7e-2 的候选，看 JSON）。

三、自检的改动

  • 总能写出 JSON：
    • run() 收到 JSON 的路径，每节之后原子地重写（临时文件 + os.replace）。
    • 每组检查与每项计时包在 _guard 里：出错时记下错误、traceback 与耗时，接着做下一项；计时的每一行、每个结构也各自 try。
    • 显存不够时清缓存后继续。
    • 退出码：0 全部通过，1 有检查失败或某一节没能运行，2 中断（Ctrl-C 等，JSON 照写，"complete": false）。
  • 次序：devices.prepare 在 capabilities 之前，让 CUBLAS_WORKSPACE_CONFIG 在 CUDA 启动前设好。
  • 精度：计时照 --dtype：float64 对应 float64 与 complex128，float32 对应 float32 与 complex64；设备没有的类型记为跳过，在 MPS 上不再崩。
  • JSON 多记（版本号 2）：
    • pydftb 的版本与安装路径；提交号只在 git 顶层包含这个文件时记（装好的 wheel 不再取外层仓库的提交号）。
    • scipy、ase、threadpoolctl 看到的 BLAS，可用的核数。
    • torch 的线性代数库、float32 矩阵乘法的精度、确定性开关。
    • GPU 的空闲显存与驱动版本。
    • 每节的耗时与显存峰值，命令行。
  • 工作负载 ptbp_workload.py：
    • 结构：PTBP 的 6 个 Cu 相（dimer、AA-graphite、diamond、beta-Sn、bcc、fcc），中心晶胞与分数坐标取自 dft.xyz，11 个 EOS 体积 V/V0 = 0.80 + 0.04 i，晶胞按体积的立方根缩放（与数据集差 ≤ 1e-14 Å，分数坐标差 ≤ 3e-9）。
    • k 网格：PTBP 的规则。Boltzmann 权重 < 0.1 的三个相只用 Γ 点，其余是 int(5·2π|bi|)。
    • 计算器：PTBP 的 _pydftb_calculator 的参数（T = 0 的 Fermi、壳层分辨、SCC 1e-5、0.01 Bohr 的差分力、多项式排斥、时间反演），SK 集合用包里的 ptbp_hcocu 的 Cu-Cu。
    • --quick 用第 0、5、10 个 EOS 点（18 个结构）。
  • PTBP 阶段的计时 time_ptbp_stage：
    • 方式：NumPy 单线程；NumPy 加 k 点线程；spawn 的进程池（--workers，默认可用核数，每个一线程，先大后小，先预热）；设备上每种精度一次（torch 一线程，先预热一个结构）。
    • 每个结构记：耗时、引擎自己的分项（build、gamma、diag、forces）、SCC 轮数、是否收敛、fill 的时间、对 NumPy 单线程的 |dE| 与 |dF|。
    • 汇总：每个结构的平均时间；GPU 对进程池、对“单线程 / P”的比；GPU 运行里留在 CPU 的工作；P 个进程先大后小的排程模拟；流水线的上限 max(CPU 工作 / P, GPU 求解)。
  • 完整一轮求解的堆叠 time_stacked_solve，取代 time_stacked（保留只计 eigh 的一列，便于与 M4d 对照）：
    • 输入：工作负载里真实的 H0、S（DFTB._setup），放到设备上。
    • 分组：Γ 点 N = 18（实数，33 个结构）、beta-Sn N = 18（复数，11 个）、bcc 与 fcc N = 9（复数，22 个）；另有 Cu 晶胞 N = 9–288 的扫描，每种 8 个 EOS 副本。
    • 逐个：每个结构 TorchSolver.prepare、求解与布居。
    • 堆叠：一次 prepare、一次 eig、一次拷回主机，每个结构各自求费米能级，一次密度，布居用一次块权重的矩阵乘法。
    • 分别计 prepare、一轮、带能量加权密度的最后一次求解、单独的 eigh、fill；给出收益与两者的最大 |Δε|、|Δμ|、|Δq|。
    • 有显存守卫，在 deterministic 下运行。
  • 命令行：--timings eigh,cu,ptbp,stacked（默认全部）与 --workers；最后几行给出结论：GPU 每个结构对 CPU 进程池、留在 CPU 的份额、堆叠的收益。

四、k 点的约化

  • reduce_time_reversal 现在对每个 k 点在 Python 里建元组、查字典，16³ 的网格约 10 ms，一个 BO 步 0.18 s（0.70%）。
  • 向量化：
    • 每对 {k, −k} 的代表取字典序较小的一个，用第一个不同分量比较；
    • np.unique(..., axis=0) 分组，按第一次出现的位置排序（即原来的次序）；
    • 权重从零起按下标次序 np.add.at 累加，与原来的逐个相加是同一串浮点运算。
    结果逐位相同，测试对比新旧实现与随机网格、偏移网格、带权重的输入。

五、JSON 的读法与 M7e-2 的判据

  • 先看留在 CPU 的工作：设一个 BO 步的 DFTB 阶段，GPU 串行时为 Tgpu，P 个 CPU 进程时为 Tpool。若 GPU 运行里留在 CPU 的工作本身就 ≥ Tpool，单把求解放到 GPU 上（包括堆叠）不会比现在快。这时 M7e-2 要同时把这部分分给 CPU 进程，与 GPU 的求解做流水线，上限是 max(CPU 工作 / P, GPU 求解)。
  • 再看堆叠的收益：完整一轮求解在 GPU 上堆叠对逐个的比，按组看。明显大于 1（例如 ≥ 3 倍），而且流水线的上限比 Tpool 小，才值得做同步 SCC。
  • 精度：float32 的结果对 NumPy 的 |dE|、|dF| 和收敛情况，决定 GPU 上能不能用 float32（M4a：T ≈ 0 的金属不宜用 float32 算力）。
  • 其他：确定性开关下的速度、显存峰值、冷启动的时间单独记录。

七、验证 开发细节

  • 自检（没有 torch 时跳过）：
    • 计时出错、检查出错与中断时 JSON 照样写出，退出码正确；
    • --dtype both 两种精度都有行；
    • 没有 float64 的设备（仿 MPS）不建 float64 与 complex128 的张量；
    • 没有 git 时照常；
    • 2 个结构、1 个进程的小阶段对 NumPy ≤ 1e-8；
    • 堆叠对逐个 ≤ 1e-12（实数与复数的分组）。
  • 工作负载：66 个结构、预期的网格与 N；PTBP 的测试里与 dft.xyz 的晶胞和坐标差 ≤ 1e-8 Å，k 网格与 PTBP 的 kpoint_grid 相同。
  • reduce_time_reversal：新旧实现逐位相同。
  • 门槛：
    • golden 两个环境逐位相同（对照 44ee7e5）；refgen（NumPy、torch、subsystems、sparse、sparse-csr、foe）；dynamics；pytest 三个环境与 MPI 环境；PTBP 测试与 G1。
    • pydftb gpu-check --device cpu --dtype both 完整与 --quick 各一次，另从 wheel 装进仓库外的干净 venv 再跑一次。

八、风险与之后

  • GPU 计时：要显式同步与预热，冷启动单独记；确定性算法较慢；cuSOLVER 按批量大小选算法，堆叠与逐个的末位会不同，所以记下偏差。
  • float32：T = 0 时费米能级的搜索可能失败，力可能差到 3e-2 eV/Å；逐个结构记录，不算检查失败。
  • 进程池：启动时间不计；核很多时排程由最大的结构决定；每个结构的时间都记下，可以按任意核数重算。
  • SK 集合：包里的 SK 集合与每个 BO 步的表不同，所以也记下每轮的时间。
  • 之后：
    • M7e-2：按 JSON 决定同步 SCC 的跨结构批量，并看要不要把 γ（只依赖几何与 U，占阶段的 24%）、原子对、费米能级与力一起处理。
    • PTBP 里每次计算的 threadpool_limits（0.6%）可以缓存，但要处理之后才加载的库，单独评估。
