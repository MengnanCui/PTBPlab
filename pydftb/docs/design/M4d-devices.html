关键信息

M4a 的 PyTorch 后端已经能把 SCC 的线性代数放到任意 torch 设备上，但只在 CPU 上验证过。M4d 补齐三件事：pydftb 按设备的能力安排计算（哪些在设备上、哪些退回 CPU）；一个由用户在自己的 GPU 上运行的自检脚本；PTBP 的 --pydftb_backend、--device、--dtype 选项。默认仍是 NumPy、CPU、float64，结果逐字节不变。

  • 本机没有 GPU。M4d 的代码在这里只能在 CPU 上验证：设备逻辑用 CPU 张量和模拟的能力表测试，退回 CPU 的分支与正常路径逐位相同。GPU 上是否正确、快多少，要由 python -m pydftb.validation.gpu_check 在用户的机器上测；任何正确性检查失败，脚本都以非零状态退出。用户运行之前，报告中 GPU 的数字一律写“未实测”。
  • 按设备能力安排。
    • CUDA（含 AMD 的 ROCm）：全部在设备上，默认用确定性算法。
    • Apple MPS：没有 float64，只能用 float32；Cholesky 分解和 float64 的求和放在 CPU 上。
    • Intel XPU 和 MPS 的本征分解、Cholesky：第一次使用时试一下，不支持就放到 CPU 上。
  • PTBP 用 GPU 时，DFTB 阶段在主进程里逐个结构计算。用了 CUDA 的进程不能再派生（fork）出也用 CUDA 的子进程，所以 GPU 不和多进程的 DFTB 阶段混用；与 --optimizer parallel_bo、pso 同用时直接拒绝。推荐器只把 GPU 列为建议，从不自动采用。
  • 先说清楚预期。M4a 实测：Cu 数据集上 torch 在 CPU 上比 NumPy 只快约一成；DFTB 阶段只占一个 BO 步的 37–57%，GPU 即使把它降到 0，一个 BO 步也最多快 1.6–2.3 倍。而 PTBP 现在用 4 个进程算 DFTB 阶段，GPU 串行算要比这更快才划算。PTBP 的矩阵只有 9–18 个轨道，GPU 处理这么小的矩阵未必快；自检脚本的计时网格就是用来回答这个问题的。
  • 4设备类型：CPU、CUDA/ROCm、MPS、XPU
  • ≤ 1e-10自检中 GPU 与 CPU（float64）的允许差
  • 0默认设置下允许改变的字节

一、目标与范围

  • pydftb：device="auto" 选第一个可用的加速器，否则用 CPU；按设备能力决定每一步在哪里算；CUDA 上默认确定性；新模块 pydftb/backend/devices.py。
  • 自检脚本：pydftb/validation/gpu_check.py，在用户的 GPU 上检查正确性并计时，输出 JSON。
  • PTBP：三个新选项（命令行、ptbp optimize、YAML、界面），运行前的检查，GPU 时 DFTB 阶段的进程模型，plan.json 记录后端和设备，推荐器的建议。

不改数值算法：设备上算的仍是 M4a 的那一套（Cholesky 化为标准问题、eigh、密度矩阵），NumPy 路径一字不改。

二、设备与能力

设备float64Cholesky、本征分解float64 的求和与 S 的分解说明
cpu有CPUCPUM4a 已验证；逐位与之前相同
cuda[:i]（NVIDIA）有设备（cuSOLVER）设备默认确定性算法（第三节）
cuda[:i]（AMD，ROCm 版 torch）有设备（hipSOLVER 或 MAGMA，取决于 torch 的构建）设备批量本征分解的速度未知，由自检的计时网格测出
mps（Apple）没有第一次使用时试；不支持就在 CPUCPU只能 dtype="float32"，选 float64 直接报错并说明
xpu（Intel）试一下第一次使用时试；不支持就在 CPU没有 float64 时在 CPU没有 float64 时与 MPS 一样处理

做法：Backend 多两个字段。linalg_device 是 Cholesky 和本征分解所在的设备，precise_device 是 float64 数组（S 的 Cholesky 因子、双精度求和）所在的设备。在 CPU 和 CUDA 上两者就是设备本身，代码路径与 M4a 完全相同。在 MPS 上两者都是 CPU：

  • S 在 CPU 上以 float64 分解，L⁻¹ 转成 float32 再送到设备；
  • 每轮 SCC 的 H′ = L⁻¹HL⁻ᴴ 在设备上算，送回 CPU 做本征分解，结果再送回设备；
  • 密度矩阵、布居、能量的迹在设备上算，求和时先送回 CPU 再升到 float64。

能力怎么知道：CUDA 视为全部支持。MPS 和 XPU 在第一次使用时，用一个 2×2 的矩阵试 float64、Cholesky 和 eigh，结果按设备缓存；失败就退回 CPU，并发出一次警告说明原因。这样不依赖文档里可能过时的支持列表；torch 以后支持了，自动就用上。

device="auto"：依次看 CUDA、MPS、XPU，都没有就用 CPU。在 pydftb 里，auto 在构造计算器时就地解析（会初始化 CUDA）。PTBP 则在一个子进程里探测（第四节），不在主进程里初始化 CUDA。

三、确定性

  • CUDA 上有些运算默认不确定：原子加法的求和顺序不固定，cuBLAS 的部分 GEMM 也不确定。所以同一台机器上算两次，最后几位可能不同。
  • 做法：DFTB 在 CUDA 上计算时，临时打开 torch.use_deterministic_algorithms(True, warn_only=True)，算完恢复用户原来的设置，不留下全局副作用。第一次选用 CUDA 时，如果环境里还没有 CUBLAS_WORKSPACE_CONFIG，就设成 :4096:8（cuBLAS 要求在第一次调用之前设好；已经初始化过 cuBLAS 的进程里设置无效，这时给出警告）。
  • warn_only 的含义：没有确定性实现的运算只警告、不报错，以免影响用户自己的其它代码。自检脚本实际检查“同一计算两次逐位相同”。
  • GPU 与 CPU 不会逐位相同：算法和舍入顺序不同，差在 1e-12 量级（float64）。自检的门槛是 1e-10。

四、接入 PTBP

选项（ptbp optimize 用连字符）取值默认
--pydftb_backendnumpy、torchnumpy
--devicecpu、auto、cuda、cuda:1、mps、xpucpu
--dtypefloat64、float32float64

运行前的检查（不满足就报错退出，说明怎么改）：

  • 这三个选项只对 --engine pydftb 有意义；--device 不是 cpu 或 --dtype float32 时，要求 --pydftb_backend torch。
  • GPU 设备与 --optimizer parallel_bo、pso 不能同用：它们用多个进程同时算 BO 点，每个进程都要用 GPU。
  • 梯度优化器（M4c）只支持 NumPy 后端：M4b 的自动求导只在 NumPy 引擎上验证过。
  • --device auto 在一个子进程里探测 GPU，结果写进运行记录；探测不到就用 CPU 并打印一行说明。

DFTB 阶段的进程模型：

  • torch + CPU：与 NumPy 一样多进程并行。父进程派生子进程之前先把 torch 设为单线程（M4a 的 fork 规则），每个工作进程用 1 个 torch 线程。torch 后端不用 k 点线程。
  • torch + GPU：在主进程里逐个结构计算。主进程初始化 CUDA 之后，PTBP 其它阶段仍会派生只用 CPU 的子进程（hotcent 分片等）；子进程不碰 CUDA，这是常见做法（PyTorch 的数据加载进程就是这样）。自检脚本里专门有一项检查：初始化 CUDA 之后派生一个跑 NumPy 计算的子进程，看它能否正常结束。

计划与建议：

  • plan.json 记下后端、设备、精度和 torch 版本。
  • GPU 时 DFTB 阶段标为“主进程、串行”，不给耗时估计：成本模型没有在 GPU 上标定过。
  • 推荐器在探测到 GPU、而用户用的是 NumPy 后端时，只打印一条建议（先跑自检脚本，再试 --pydftb_backend torch --device cuda），从不自动改用。

五、GPU 自检脚本

python -m pydftb.validation.gpu_check                         # 自动选设备，全部检查和计时
python -m pydftb.validation.gpu_check --device cuda:1 --json gpu_check.json
python -m pydftb.validation.gpu_check --quick                 # 子集，约几分钟
部分内容判据
环境torch、CUDA/HIP 版本，设备名、显存、算力；NumPy、Python、CPU 型号、核数；能力表（第二节）只记录
参考算例冻结的 DFTB+ 参考（tests/data/ref）在设备上重算与 refgen --check 相同的容差
与 CPU 对照同样的算例在 torch CPU 上float64：能量、力、电荷 ≤ 1e-10；float32 只报告
确定性同一计算算两次逐位相同
自动求导小算例上 hf 与 implicit 模式的梯度，以及与 CPU 的梯度≤ 1e-9
fork（只对 CUDA）子进程里初始化 CUDA、算一次，再派生只用 CPU 的孙进程算 NumPy60 s 内正常结束
计时：本征分解网格N = 9–288 个轨道 × 批量 1–2048 × float64/complex128/complex64，设备与 NumPy 的耗时只报告
计时：Cu 结构与 PTBP 同样设置的 Cu 晶胞（不同 k 网格）：NumPy 单线程、NumPy k 点线程（全部核心）、设备只报告
计时：多结构堆叠把多个结构的 k 点矩阵堆成一批做本征分解，与逐个结构做比较只报告：决定以后要不要做跨结构的批量

输出：终端上一张摘要表，加一个 JSON 文件（环境、每项检查的数值和结论、计时）。任何一项正确性检查失败，退出码为 1。用户把 JSON 发回来，就能据此决定 GPU 是否值得用、跨结构批量是否值得做。

八、不做的事与风险

  • 跨结构的批量（把很多结构的 k 点矩阵合成一批、同步 SCC）：等自检的“多结构堆叠”计时出来再决定（M7 或单列 M4e）。
  • GPU 的成本模型：这里无法标定，不做；GPU 时 DFTB 阶段不给估计。
  • 机器指纹加入 torch（计划里的 D4）：不做。指纹只用来缓存 NumPy 的探测结果，torch 的版本不影响它；等有了 torch 自己的探测再加。
  • MPS、XPU 只保证能运行：本机和 CI 都无法检查它们的正确性，自检脚本是唯一的检验手段。
  • 多 GPU、GPU 上的梯度优化器、GPU 上的 SP2 与能带：不做。
  • 风险：
    • 主进程用过 CUDA 之后再派生子进程：子进程只用 CPU，自检里有专门的检查。
    • 确定性模式变慢：只在 DFTB 计算期间打开，自检会给出耗时。
    • 小矩阵上 GPU 不划算：如实报告，不改默认值。
