关键信息

M7d2 之后，4913 个水分子用分治（4 个进程）仍超出 13.36 GiB 的作业上限。M7d2 报告第八节列了原因：子体系在图样上的索引在主进程里为全部子体系建好再 fork，每个工作进程的调用栈都留着整份；工作进程各自存 S、H、P、W 在整个图样上的副本；SK 原子对建立时临时多出 3.86 GiB。M7d3 只改内存的组织，不改任何数值：结果对 M7d2 逐位相同，没有新的用户选项。

  • 子体系的索引：每个图样元 40 字节（行、列 int32，位置 int64，核心部分再存一份行、列、位置与 float64 的分区权重）改为 9 字节：子体系块里的平铺位置 lin = r m + c 与图样位置 g，放得下时都用 int32；p > 0 的元排在前面（不再复制），分区权重只留一个布尔数组（p = 1 或 1/2）。
  • 谁建索引：主进程只做划分，把每个工作进程的（核心、子体系原子）与图样交给它，工作进程在 fork 之后自己建；主进程不再有全部子体系的索引，工作进程也不再继承别人的。MPI 的进程本来就这样。
  • 收发多少：工作进程只收发自己的子体系用到的图样元（used，建好索引后发回一次）：S、H 只发这些元，P、W 只回这些元，主进程 rho[ik, used] += part。为了让 used 小，工作进程拿连续的一段核心（格子的次序，空间上相邻），各段的代价 m3 大致相等；子体系少于每个进程 8 个时照旧“最大的先给最空的”。
  • SK 原子对：探针发现 M7d2 报告把建立时的临时峰值归错了：邻居表本身很小（1728 个水分子 0.22 GiB），大头是 SKTable.evaluate 为整组原子对取出的样条系数 coef[ii]（每对 8 × 20 个 float64，约 1.3 kB，每个文件一次），加上复数步长的复数块与最后的 concatenate。build_pairs 改为先算出元的总数、分配最终的数组，再按块（至多 214 对、218 个元）填进去。
  • 40 → 9子体系索引每个图样元的字节数
  • 0.94 → 0.061728 个水分子 build_pairs（带导数）的临时峰值（GiB）
  • 0改变的位（分治的结果、SK 原子对的每个数组）
  • 0新的用户选项

一、范围

  • 做：
    • subsystems.py：紧凑的索引、工作进程自己建索引、只收发用到的图样元、连续的分配；MPI 与 fork 的工作进程同一套协议；
    • hamiltonian.build_pairs：按原子对分块，直接写进最终的数组；
    • 工作进程建索引出错时，主进程报出它的错误（原来出错在主进程里）。
  • 不做：
    • 不建 γ（N × N，4913 个水分子 1.62 GiB）：要每轮 SCC 用结构因子算电势，改变 SCC 的每一轮，单独做；
    • 工作进程里的本征矢（从本征分解留到密度，4913 个水分子合计约 1.9 GiB）：是算法要的，只换存法不省；
    • PairBlocks 的字段类型（行、列、对的编号仍是 int64）：它们是别的模块用的公有字段；
    • perfmodel 的重新拟合：它的 sk_pairs 一项在小体系上拟合，那里省下的 concatenate 副本占比很小，估计只是偏保守。

二、探针

  • 量法：这台机器是 macOS（32 GB）。RSS 把 fork 共用的页算进每个进程，整台机器的“已用”受内存压缩影响，都不可靠。改用每个进程的物理占用（proc_pid_rusage 的 ri_phys_footprint，与“活动监视器”的“内存”相同）：fork 继承、没有改写的页只算在父进程上，子进程只算自己复制或新分配的页（探针：父进程 1 GiB，子进程 fork 后 0.002 GiB，改写 0.25 GiB 后 0.25 GiB）。所以各进程之和就是真实的总量。每 0.5 s 采样一次，另记每个进程的终生峰值。
  • SK 原子对（tracemalloc，带导数，ptbp_hcocu 的 H s、O sp，截断 15.36 Bohr）：
    • 邻居表本身：512 个水分子保留 0.024、峰值 0.065 GiB；1728 个保留 0.080、峰值 0.219 GiB。
    • 整个 build_pairs：1728 个水分子保留 0.478 GiB，原来峰值 1.417 GiB（多出 0.94），只按元数分块（每块 218 个元）峰值 1.136 GiB：H–H 每对一个元，一块仍有 26 万对，样条系数照样大。再按对数封顶（214 对）后 0.538 GiB（多出 0.06），时间 20.7 → 14.6 s。
  • 单对的块：只含一对的块让复数步长的导数在最后一位不同（≤ 2.8e-17）。一对时 numpy 的堆叠 matmul（sk_block 里的 Da M DbT）走另一条路；两对以上的任何块都逐位相同（逐个试了每块 2–64 对与各种余数）。所以块至少两对，一组只有一对时整组一块（与原来相同）。

三、方法

  • 索引（_index）：从图样的位置矩阵取子体系的主子块（COO），算 keep = core[r] | core[c]，稳定排序把 keep 的元放前面（nk 个），存 lin、g、nk、both = core[r] & core[c]（前 nk 个）。稠密块：a.reshape(-1)[lin] = data[g]；密度：rho[g[:nk]] += p · d.reshape(-1)[lin[:nk]]，p = where(both, 1, 0.5)。
  • 工作进程（_Workers、serve）：参数是自己的（核心、子体系原子）列表与图样（indptr、indices、n、offsets、norb_atom，主进程本来就有）。启动后建索引、求 used（全部 g 的并集，排好序），把 g 改写成 used 里的下标，发回 ("used", used)；出错发回 ("error", …)，主进程关掉全部工作进程再抛出。set_overlap 与 eig 给每个进程发 s[used]、h[used]，MPI 用 scatter 代替 bcast。
  • 分配（_assign）：子体系数不少于 CONTIGUOUS_MIN（8）× 进程数时，按代价 m3 的累加和切成进程数段；否则照 M7d。核心按格子的键排序，所以一段是几层相邻的格子。
  • SK 原子对：先按元素对分组（与原来相同的组与次序），算出总元数，分配 rows、cols、pair_of、h、s 与 dh、ds；每组按块取 vec[sel]，块的结果写进 [e0:e1] 的视图；dh、ds 的视图按原来的形状 (对, a, b, 3) 写。

四、为什么逐位相同

  • 索引：同一个子体系的元集合相同，每个元的值相同（p 是 0.5 · (1 + 1) = 1 或 0.5 · (1 + 0) = 0.5，原来也是这两个数）；花式下标的 += 在一个子体系里不重复，次序无关。
  • 分配与只收发用到的元：每个图样元最多两份贡献（它两个原子所在的核心），浮点加法可交换，(0 + a) + b = (0 + b) + a；没有贡献的进程原来加的是 +0，而所有部分和都从 +0 起加，不会是 −0，x + (+0) = x。所以分配怎么变、少加多少个 +0，都不改变任何一位。
  • SK 原子对：每个值只由它自己那一对算出（样条、转动、sk_block 都是逐对的），块只改变一次算多少对；唯一的例外是一对的块（第二节）。

五、验证

  • 新的 tests/test_dc_memory.py：紧凑索引对 M7d 的索引（同一元集合、分区权重、稠密块、密度贡献逐位相同）；used 的下标；连续分配（每个子体系一次、一段连续、负载差不超过两个最大的代价）；216 个水分子 4 个进程每个都少于图样的 80%，结果对单进程逐位相同；工作进程出错时报错；build_pairs 在 5 种块大小下对默认逐位相同（水与 Cu，无导数、复数步长、有限差分）；分子与没有原子对的情况。
  • test_processes_give_the_same_bits 多一个 4 个进程（27 个子体系，走“最大的先”），1 与 2 个进程走连续分配。test_workers_exit_with_the_master 在没有 /proc 的系统（macOS）上用 os.kill(pid, 0)。
  • 门槛：全套 pydftb 测试、refgen --check（eigh 与 --solver subsystems）、golden --base c1a11bd；1728 与 4913 个水分子的 SCC 加力对 M7d2 逐位相同，并量内存与时间。

六、风险与之后

  • 连续分配的负载：代价相近的子体系（水）切得很匀；大小差得多时（界面、团簇）一段可能偏重，最多差一个最大子体系的代价。子体系少时照旧用“最大的先”。
  • fork 的副本：工作进程仍继承 fork 时主进程的全部页（SK 原子对、图样），只是不改写就不占内存；主进程之后放掉的大数组在工作进程退出前不会还给系统。现在 fork 发生在建立 Coulomb 之前，主进程那时只有 SK 原子对与图样，它们在 SCC 里本来也要留着。
  • 之后：不建 γ 的 SCC 电势；ThirdOrder 的 Γ3、色散的参数矩阵等其余 N × N 数组。
