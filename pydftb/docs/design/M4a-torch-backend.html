关键信息

M4 的第一步：pydftb 的重计算（k 点折叠、Cholesky、本征分解、密度矩阵、Mulliken 布居、能量的迹、力用到的实空间密度）可以放到 PyTorch 上，在 CPU 或 GPU 上算；几何、参数、γ、混合器和费米能级搜索仍是 NumPy。用 DFTB(backend="torch", device=..., dtype=...) 打开，默认仍是 NumPy，NumPy 路径的结果逐位不变。

  • 为什么先做前向：M4b 的自动求导和 M4d 的 GPU 都建立在它上面；也先得到 torch 与 NumPy、与 74 个 DFTB+ 参考的对照基线。
  • 对照的门槛：torch（CPU、float64）与 NumPy 在 SCC 收敛到 1e-12 时，能量 ≤ 1e-10 Ha，力和电荷 ≤ 1e-9，本征值 ≤ 1e-10 Ha，SCC 轮数相同；74 个参考用原来的容差全部通过。NumPy 路径用新的 golden 工具与 M4 之前的提交逐字节比较中间量和结果。
  • 先说清楚的预期：4 核上 PTBP 一个 BO 步里 DFTB 阶段只占 27.1 s 中的 10.0 s（energygeometry）和 18.0 s 中的 10.3 s（dataset），即使 GPU 把它降到 0，一个 BO 步最多快 1.6 倍和 2.3 倍。torch 在 CPU 上单线程和 NumPy 差不多（探测：k 点堆叠的本征分解快 10–25%）。
  • fork 的坑（实测）：父进程用多线程跑过 torch 后再 fork，子进程只要不先设线程数就全部卡死（4/4）。规则：父进程保持 1 个线程，子进程先设线程数再算。
  • ~1e-15torch 与 NumPy 本征值的相对差（探测）
  • 237golden 逐字节比较的计算（41,519 个量）
  • 0NumPy 路径允许改变的位

一、目标与现状

M0 的设计目标是“换 PyTorch 时不需要重写物理代码”，为此建了 backend/ops.py。实际情况是 ops.namespace() 没有任何调用者，约 2,600 行数值核心直接调用 NumPy（约 630 处 np.），输入处 np.asarray(..., float)、输出处 float()。M4 因此分四步：

子阶段内容
M4a（本文）设备上的线性代数；setup 全部仍用 NumPy
M4b核函数（SK 插值与旋转、γ、Ewald、三阶、排斥势）改成与数组库无关；pydftb.autodiff：可微参数、密度矩阵的差商反向、SCC 隐式微分
M4cPTBP 损失对 r0_w、r0_d 的梯度，可选的梯度优化器
M4d设备选择、GPU 自检脚本、PTBP 的后端选项

M4a 只动计算流程里“每轮 SCC 都要做、而且随 k 点数和轨道数增长最快”的部分。这样 NumPy 路径只改约 150 行，而且都是“把 np. 换成 xp.”或“在边界处转换”，逐位不变容易保证。

二、设计

1. 后端对象

Backend(name, device, dtype)：name 为 "numpy"（默认）或 "torch"；device 为 torch 的设备名（M4a 测 "cpu"，M4d 再做 GPU 的选择与检查）；dtype 为 "float64"（默认）或 "float32"。DFTB、PyDFTB、pydftb.SCC 都加这三个选项。NumPy 后端下它的各个转换函数都是原样返回，所以 NumPy 路径上的每个运算仍是同一个 NumPy 调用。

2. 数据流：哪些在设备上

步骤位置说明
setup：邻居表、SK 块及其导数、onsite、γ、Ewald、三阶、色散主机 NumPy与原来完全相同
折叠到 k 点实空间块在主机累加；相位矩阵在主机算；相位 GEMM 在设备上主机部分与 NumPy 逐位相同，所以两个后端的 H0(k)、S(k) 只差在一次矩阵乘法
Cholesky 与 L⁻¹设备，float64cholesky_ex + solve_triangular（不用批量 LU：pytorch#142815）；与 SciPy 的 driver="gvd" 是同一个算法
每轮 SCC：电势主机γ·Δq（和三阶、自旋）是长度为位点数的小向量，传到设备
每轮 SCC：H = H0 + ½S∘(vμ+vν)、本征分解、密度矩阵 ρ 与 W、Mulliken 布居设备同一段代码，xp 为 numpy 或 torch
每轮 SCC：占据数与费米能级主机本征值每轮拷回一次，沿用 DFTB+ 的规则（occupations.fill）；占据数再传到设备
每轮 SCC：混合与收敛判断主机Broyden 与原来相同，所以 SCC 轮数可以与 NumPy 一致
能量设备上算 Σk wk Tr(ρkH0k)，其余主机结果是 Python float
力与应力设备上按平移 T 把 ρ、W 折回实空间并取出原子对上的元素；之后的收缩在主机只传回与原子对元素个数相同的两个向量

DFTB.calculate 对两个后端都是 NumPy 输入、NumPy/float 输出，PTBP 和 ASE 看到的类型不变。

3. float32

H、本征分解、密度矩阵和布居用 float32（k 点时 complex64）；S 的 Cholesky 和 L⁻¹ 仍在 float64 下算，再转成 float32；主机上的一切（电势、费米能级、混合器、能量的累加）都是 float64。float32 下 SCC 容差小于 1e-6 时给出警告。精度只报告，不作承诺。

4. 线程

torch 的线程数不受 threadpoolctl 控制。PyDFTB(threads=n)（PTBP 默认 1）在 torch 后端下用一个上下文在计算期间设 torch.set_num_threads(n)，结束后恢复。torch 后端不用 k 点线程（k_threads > 1 时警告并忽略）。fork 的规则见关键信息：PTBP 的工作进程在算之前先设线程数（M4c、M4d 接入时落实）。

5. NumPy 逐位不变

  • 只做 np. → xp. 的替换，不改运算的结合顺序；NumPy 专用的写法（SciPy 的 COO、np.add.at、bincount、einsum 的路径）原样保留在 NumPy 分支。
  • python -m pydftb.validation.golden --base 65115d1：在工作区和基准提交的 git worktree 里各跑一遍同样的计算（每个参考算例用 eigh、batched 两个求解器和 DFTB+ 的差分步长，各动力学参考的前几步，PTBP 设置下的 Cu 晶胞），逐字节比较所有结果字段和中间量；两个 Python 环境都跑。
  • import pydftb 和 NumPy 后端的计算不导入 torch（有测试）。

开发细节五、验证计划
  • G0（NumPy 不变）：golden 两个环境逐字节相同；pytest pydftb/tests；refgen --check（74）；dynamics --check（11）；test_kthreads。
  • G1（PTBP 不变）：pytest tests；test_dftb_stage_parallel.py；tools/engine_parity.py --compare-serial 在已发表的 Cu 点两种模式，损失逐位不变。
  • G2（torch）：refgen --check --backend torch 和 dynamics --check --backend torch 用原来的容差；pydftb/tests/test_torch_backend.py（水、Cu fcc 含 T≈0、Cu8 MP2、CuO 自旋、DFTB3、GdO f 轨道、D3 作为常数项；SCC 1e-12 时 E ≤ 1e-10 Ha、F 和 q ≤ 1e-9、ε ≤ 1e-10、SCC 轮数相同）；test_reference.py 按后端参数化（SCC 轮数 ±1）；test_torch_fork.py（子进程里探测，带超时）；test_import_hygiene.py。最小环境（无 torch）下 torch 测试跳过；venv 和 conda 环境都跑。
  • float32：同一组算例的能量、力、电荷、SCC 轮数与 float64 的差，只报告。

六、局限与不做的事

  • setup 仍是 NumPy：大体系的 H0 在主机建好再传到设备（M4b 起核函数可在 torch 上算，M7 再考虑大体系）。
  • torch 后端不支持 SP2、能带和 DOS、k 点线程。
  • torch 与 NumPy 不逐位相同（MKL 与 OpenBLAS），只承诺上面的容差；同一 torch 版本、同一线程数下可复现。
  • GPU 在这里测不了，留给 M4d 的自检脚本；本阶段的代码不假设设备是 CPU。
