本轮（日志清理）细节

  • 噪音根因：customtkinter 6.0.0 在 <Configure> 事件里调用 _draw，而某个 CTkFrame 子类的 _canvas 尚未赋值（为 None），触发 None.winfo_exists() 的 AttributeError——无害但会打印整段栈。
  • 修法：新增 gui/core/logging_setup.py，在 Tk 根上安装 report_callback_exception 处理器：识别并静默这条已知良性异常（记 DEBUG）， 其它真实异常则以干净一行 + DEBUG 完整栈输出。
  • 更干净：子进程每行去 ANSI 色码；合并日志改为信息框头/尾 + 耗时 + 产物清单。
  • 验证：xvfb 下重跑并循环全部 7 个视图，winfo_exists / “Exception in Tkinter callback” 出现次数 = 0，stderr 全净。

B · 软件信息

架构：两层

gui/core/ · 纯 Python，不依赖 Tk，无显示可单测
  • structure_tools.py — 体积缩放/EOS 序列/位置微扰/摘要（仅 ASE）
  • gui_state.py — 复用 SetupState 生成 YAML/命令
  • runner.py — JobRunner 子进程 + 合并日志
  • env_doctor.py — 依赖体检
  • logging_setup.py — 日志 + 去色码 + 噪音屏蔽
Tk 层 · 薄皮，只做界面
  • theme.py — VSCode 调色板/字体/圆角
  • widgets/ — sidebar / card / form / log_panel / mpl_canvas
  • app.py — 主窗口 + 活动栏 + 视图切换
  • views/ — 7 个视图
设计意图：所有逻辑放进无 Tk 的 core/，因此在没有显示、没有 DFTB+ 的环境里也能完整测试；Tk 层尽量薄。重计算通过子进程调用 ptbp， 只在装了 conda-only 依赖的机器上真正计算。

D · 使用逻辑（端到端工作流）

典型流程：从结构到优化

1) Structures 加载单结构 → 生成 EOS 训练集 (90–110%, 11 点) → 保存 dataset.xyz
2) Optimize 选数据集 → 目标(能量+力) → 优化器(bo/pso) → 参数(r0_w r0_d sigma_rep)
3) Preview 生成 ptbp_run.yaml + 等价命令（默认只预览）
4) Run 点“运行” → 子进程跑 ptbp optimize → 实时流式输出 + 合并日志
5) Monitor 自动接住运行文件夹 → 收敛曲线 + 最优参数 + 产物浏览
6) Logs 查看单一 gui_run_<ts>.log

生成 SKF（无需数据集）

Generate 符号 H O Cu → 参数集 PTBP → full → 预览命令 → 运行（需 hotcent/pylibxc）
核心心智模型：预览 → 运行。 优化与生成默认只预览（生成 YAML + 命令，零依赖）， 运行是显式按钮。真正计算需要 DFTB+/hotcent/pylibxc；缺依赖时“计算器”视图会告诉你差什么。

E · 已知限制与非目标

  • 无 DFTB+/hotcent/pylibxc 时无法实际计算——运行按钮已接线，缺依赖只会在日志里报错，不会崩。
  • 结构预览为 2D matplotlib 投影（轻量），非交互式 3D。
  • bandstructure 优化路径在 cli/run.py 中有既有 bug （本轮按约定未修）；界面“带隙”目标已就绪，修复该路径后即可用。
  • 工具箱底层 print → logging 的全量重构未做（属更大改动）。
